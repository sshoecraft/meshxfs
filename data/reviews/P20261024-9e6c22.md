## 1. The cause is proven by instrumented evidence, not inference

## 5. Does any other code path have the same defect the fix does not cover?

The question: does any other code judge a LUN owner alive from the start time in /proc/<pid>/stat alone? I searched in two ways.
- **Owner files.** `tools/lun_pool.sh:114` `owner_of() { echo "$POOL/lun$1.owner"; }` is the only place an owner file is located. A grep of tools/, scripts/, tests/ and run.sh for `.owner`, `owner_live` and `kill -0` found no reader of a pool owner file outside lun_pool.sh.
- **Start-time checks.** A grep for `starttime`/`start time` found three users of field 22:
  - `tools/lun_pool.sh:193`, the helper `starttime_of`.
  - `tools/lun_pool.sh:594`, `alloc`'s check of its own claimant (below).
  - `tests/suite/lib.sh:119` `suite_proc_starttime`, a node-side watchdog over the test's own main shell. It has nothing to do with LUN ownership.

Inside lun_pool.sh, every liveness decision about an existing allocation calls `owner_live`, which now holds the fix:
- `:505` reclaim_stale
- `:553` up
- `:600`, `:623`, `:660` alloc

The other holder processes in drbd_rig.sh (`HOLDERS+=` at `scripts/drbd_rig.sh:1509` and `:1628`) also allocate through `"$POOL" alloc`, so the same owner_live judges them.

One check is not covered by the fix: `tools/lun_pool.sh:594` `    local st; st=$(starttime_of "$owner")` / `:595` `    [ -n "$st" ] || die "owner pid $owner is not running"`. This checks the claiming owner at alloc time, not an existing allocation's owner, and it cannot produce the record's failure (a node refused because a dead owner is read as live).
