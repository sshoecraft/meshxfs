## Verdict: REJECT

The batch's own statistics hold. It was declared after the freeze and before its first lap, N = 6 is correct for 10/10 at δ = α = 0.005, and six of six laps passed with the probe, with none failed or dropped. The in-process evidence for the fix's mechanism is good: the same binary, with only DL_SHORTCUT_CLAIM changed, fails 10 of 10 with the knob off and passes 6 of 6 with it on. The decision cannot be applied anyway, because two of its conditions are not proven:

1. **The laps did not run on the candidate named.** Each lap rewrote `tests/tauth/adopted_grant_handoff_test`, a file in candidate 0.90.134's frozen manifest. Its inode went from 98566229 to 98566218 and its ctime from 01:02:44.173Z to 02:26:52.823Z. The candidate tool reports that as "touched", and the release process says any such change makes the candidate INVALID. Lap 1 caused the drift and laps 2-6 ran after it. Step 6 of the same lane also changed the content of `tests/tauth/fenced_node_ledger_test`. The candidate and build fields on the six rows are an environment variable and a `modinfo` of a module no lap loads. Because a `verified_at` mark matches by version only, applying this batch would carry the mark into the attempt that must replace this INVALID one, which these laps never ran on.
2. **No lap ran at the configuration being cleared.** Every lap was four simulated nodes in one process on the lab host: no VM, no multipath, no kernel module. The probe is a test's stdout line. Applying the batch would retire 8/net/mesh/mpath:path_peer_withdrawn:2026-10-22T19:58:42Z, the rig run in which test21 shut its filesystem down, which also measured a 75 s stall and a test28 mount timeout. No 8/net/mesh/mpath board row has run on 0.90.134, and the record's own `next` still calls for path_peer_withdrawn on the candidate's module.

What is missing:

- Laps recorded after the freeze of a candidate attempt that has not drifted, with `tools/release_candidate.py check` still clean after the last lap. As written, this harness cannot meet that, because `tests/tauth/adopted_grant_handoff_test.sh:25` writes a frozen file on every lap. The current attempt has already drifted on two files.
- Exposure of the trigger at 8/net/mesh/mpath on the candidate's module: laps of the configuration itself, whose node kernel logs show the probe. If those laps are sized from this in-process control's rate, that is a transfer of a rate from one setting to another (`docs/release-process.md:380-381` `- **The transfer assumption.** Using a rate measured at one configuration at another assumes that` / `  the failure rate given exposure does not depend on configuration. ...`). The proposal has to state why the rate carries over so the reviewer can check it. Because the control is labelled `8/net/mesh/mpath`, `plan-verify` would never ask for that `--transfer` (`tools/defects.py:1052`).
