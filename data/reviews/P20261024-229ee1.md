What the late path carried, measured. The late path is sdb (path a): it is the one that fails when path a is taken down, `tests/evidence/board_lrc221_20261024T205839Z_late_register_hold/links.log:1` `san_net: test16 a down 2026-10-24T20:58:52.019Z`, and `.../state_test16_a_failed.txt:2`:

- control lap 1 start, `.../board_lrc221_20261024T205839Z_late_register_hold/state_test16_start.txt:2`: `PATH sd=sdb ... dm=active chk=ready dev=running reads=912 writes=1030`

Over the same span the other path (sda) went from `reads=69558 writes=51176` (`board_lrc221.../state_test16_start.txt:1`) to `reads=386820 writes=287634` (`board_lrv221.../state_test16_a_back.txt:1`). So the counters are live. On this rig the map sends all of test16's data I/O to sda, and none to sdb, even while sdb is `dm=active chk=ready`. That holds with the fix off as well. In this lap the late path carries none of the node's reads or writes, so a node write queued behind the delayed REGISTER, the hazard the lap names at :9-11 and :38-39, cannot happen in either arm.

The control's own figures agree. All 10 control rows, `data/criteria.runs.jsonl:15882` through `:15997`, have the same reason:
> LAP late_register_hold FAIL 2 check(s): writes_done=0 requests_sent=7 held=0

That is writes_done=0 in every fix-off lap. Its two failing checks are:
- `held=0`. This is the module reporting that pr_fill_hold is 0 (`board_lrc221.../knobs.txt:4` `test16 pr_fill_hold want=0 got=0`). It fails by construction whenever the fix is switched off, so it carries no information about the defect.
- `requests_sent=7`. The count is the same in all 10 laps. The read/write counters of sdb did not move, so these 7 were not data I/O. They fit the path checker's TEST UNIT READY at `polling_interval=2 s` over the 15000 ms window. The lap counts those explicitly (:40), but they are not the hazard.

So the control's "10 of 10" is a rate of the switch being off, plus multipathd's checker. It is not a rate of the defect's trigger. A verification sized from it, whose PASS is `held=1 requests_sent=0 writes_done=0` while the late path never carried I/O in either arm, shows that the quiesce mechanism engages and blocks the checker. It does not show that the configuration no longer has the defect. The EXPOSED line in each of the six PASSes is met by sda's traffic alone, so none of the six is an exposed trial of the hazard.

## Verdict: REJECT

The batch was declared before its first lap, and N = 6 is correct for a 10-of-10 control at δ = α = 0.005. All six laps are PASS rows on candidate 0.90.134, build A7E90BC5313192108E35B80, with none failed or dropped. The verification still proves nothing about the defect. The exposure probe fires when the load completed operations through the map, by any path. The rig's own path counters show the late path (sdb) carried no data I/O at all, from control lap 1 through verification lap 1, with the fix on or off. The control's 10-of-10 FAIL comes from `held=0`, which is the fix's switch, and `requests_sent=7`, which are non-data commands (writes_done=0 in every control lap). Neither is the hazard the lap names: a node write dispatched down the late path behind an unresolved REGISTER.

What is missing:
1. A control in which the late path carries the node's data I/O, so that with pr_fill_hold=0 a write is dispatched down it while the REGISTER is unresolved (writes_done > 0, or at least data requests in sdb's read/write counters). Today the path selection or grouping keeps all I/O on sda.
2. A control whose FAIL does not include `held`, the fix's own flag. Its rate must be a rate of the hazard, not of the switch.
3. An exposure probe that shows, in each counted PASS, that the late path was in the map's active selection while the REGISTER was unresolved, so that without the hold the node's I/O would have gone down it. Then a verification sized from that control's measured rate.

The record also says the lap measures a proxy and does not reproduce a REGISTER executing after a fence (`tests/late_register_hold_lap.sh:18`). A removal will need its own evidence for that link. This review does not rule on it.
