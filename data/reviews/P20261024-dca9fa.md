Both batches ran only at 2/disk/caw/direct
(`tests/evidence/lanes/g2c_a22_20261024T204638Z/summary.log:1` `holds configuration 2/disk/caw/direct`).
Neither set NOINO_RING_ROTATE, and every lap took the test-only exit at
`tests/noino_fence_efd_hold_lap.sh:161` `[ "${LAP_ABORT_AFTER_LOAD:-0}" = 1 ] && { echo "RESULT: ABORT label=$LABEL stage=forced ...`
on a pair that answered at once (e.g. `batch_laps/b20261024-63b965/20261024T211301Z-7fcf860e.log:4` `RESULT: ABORT label=lsv221 stage=forced`).

So the argument's statement that "exposure is the record's trigger, not a proxy" does not hold.
The record's ABORT happened at `noino_fence_efd_hold_lap.sh:171-175` after S stopped answering
`rs` within its 60 s bound, following a fill of up to 400000 /dev/kmsg records under the network
lock manager. The fix's stop is itself an `rs 60` to that same node
(`tests/lib/lap_load.sh:42` `        rs 60 "$n" "$cmd" > "$out/${n}_load_end.txt" 2>&1 &`), issued
right after. If the node's rs is still timing out, the stop file is never touched and the load
runs on, which is exactly the record. That precondition was never present in either batch.

The proposal carries the 2/disk/caw/direct result to 2/net/mesh/direct by reading code ("the
defect is in the rig lap's shell exit path, which has no lock-manager or attachment dependence").
Reach and carry-over have to come from runs on the configuration, never from reading code. The
record's own next step planned "a control and verification at 2/net/mesh/direct, where the
failure was seen", and that was not done.

The proposal's cause text also claims the trap ends the loads "on every exit path". The lap's
callers bound it with `timeout -k 5`
(`tests/lap_load_end_lap.sh:64`, `g2_a20 summary.log:20`), which SIGKILLs 5 s after the TERM,
while the trap needs up to 45 s of wait (`tests/lib/lap_load.sh:16`). No lap measured that exit,
so "every exit path" is asserted, not measured.

## Verdict: REJECT

The control (10 of 10) and the fix-on batch (6 of 6, correctly sized, every lap exposed and each
load ended by its stop file) prove the trap stops a running load after a plain forced `exit 2`
on a responsive pair at 2/disk/caw/direct. They do not prove the record is fixed, for these
reasons:

1. No run was made at 2/net/mesh/direct, where the defect was seen. The carry-over is argued
   from code, which is not evidence of reach.
2. The record's trigger was never exercised: an ABORT after S's `rs` timed out (rc=124) under
   the ring-rotation fill. The fix's stop path depends on that same node answering `rs` within
   60 s.
3. The fix-on batch's verify (P20261024-00fcf0) is unreviewed and the batch is still open.

What would make this approvable:
- A control batch (LAP_LOAD_STOP=0) and a fix-on batch sized from it, run at 2/net/mesh/direct.
- The lap's ABORT driven through the record's own path: NOINO_RING_ROTATE=1 with S's rotate
  measure overrunning, or an equivalent `rs` timeout on S after the loads start, rather than
  `LAP_ABORT_AFTER_LOAD=1`. Each lap's exposure should show the load was running when the lap
  exited and that S's `rs` had timed out.
- The verify of the fix-on batch approved before the removal.
- Measured evidence for the `timeout -k 5` kill exit, or the cause text narrowed to the exits
  that were measured.
