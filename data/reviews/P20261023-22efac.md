## Verdict

The batch's bookkeeping holds. It was declared before its first lap. N = 6 is correct for the
control's 10 of 10. All six laps are PASS with exposure, none failed and none was dropped.

The proposal is rejected for two reasons. Either one is enough on its own.

1. **The laps did not run on the candidate as named.** Every lap ran on a pair prepped with
   `MXFS_EXTRA_MODARGS=dead_timeout_ms=12000`. That is a module argument applied at insmod, and
   it is not the candidate's default: `dead_timeout_ms` 0 means 34 s on SCSI. run.sh defines such
   a run as a VARIANT that "never grades a release candidate". defects.py counts no verification
   lap that has any variant at all. The original failing run recorded this exact variant. The six
   laps carry none only because `tools/batch_lap.py` records the batch's own variant and never the
   environment's module arguments. The ledger rows' empty variant field is a recorder gap, not
   evidence that the laps ran the candidate's configuration.
2. **The laps never reach the trigger of the record's stability failure.** Approving would retire
   the record's failing run `2/disk/caw/mpath:path_mount_degraded:2026-10-23T16:57:29Z`. That run
   had a 41.6 s stall, over `stall_limit_s` = 30. It also had 1.4 M errored operations and a
   withdrawal on every node. The lap runs only path_mount_degraded's steps 1-3. It puts no load on
   the victim and never fails the path left standing after the reinstatement. That second failure
   is the step where, by the record's own log sweep, the unregistered path refused a write and the
   filesystem shut down. So `EXPOSED` shows the precondition: a one-path mount with 3 of 4 keys. It
   does not show the shutdown/stall trigger. The causal step from "late path unregistered" to
   "shutdown and stall" is read from log order, not measured. The record's own next step asks for
   path_mount_degraded at 2 and 4 nodes on the 12 s window, and no path_mount_degraded run exists
   on the candidate.

One more thing, which is not a reason for the verdict. The proposal's `data/defects.json` line
citations are stale, and so is the proposer's corrected offset. The control and verify batches are
at `data/defects.json:5594-5609` and `:5610-5642`. The argument cites :5718-5732 and :5735-5765.
The note says they moved +38, to about :5756 and :5773-5803, which is also wrong. I located both
batches by id, and their content matches what the argument quotes.
