## 4. The lap exercises the record's actual trigger

The record's cause is that batch_lap.py's subreaper keeps the holder killed by `drbd_rig.sh up` a zombie, and that owner_live reads the zombie as live for the next drbd_rig.sh step. The pieces:
- Subreaper: `tools/batch_lap.py:271` `    become_subreaper()`.
- Normal path waits only for its direct child: `tools/batch_lap.py:275` `        return proc.wait(timeout=bound)`. Orphans are reaped only on the overrun path, `tools/batch_lap.py:241` `def reap(proc, lap: dict) -> None:`.
- Holder killed at `up`'s exit: `scripts/drbd_rig.sh:249` `end_holders() { [ "${#HOLDERS[@]}" -gt 0 ] && kill "${HOLDERS[@]}" 2>/dev/null; return 0; }` and `:250` `trap end_holders EXIT`.
- The second step adopts: `scripts/drbd_rig.sh:3652` `    mxfs)   evid; take_locks; hold_luns adopt; step_mxfs ;;`.
- The lap runs `up` and `mxfs` as separate processes, with a probe between them that reads only field 3 of `/proc/<pid>/stat`: `tests/drbd_zombie_holder_lap.sh:42` `out=$(scripts/drbd_rig.sh up 2>&1)`, `:55` `    [ -n "$pid" ] && { s=$(cat "/proc/$pid/stat" 2>/dev/null); s=${s##*) }; st=${s%% *}; }`, `:59` `[ -n "$zombies" ] && echo "EXPOSED: up's holder is a zombie when mxfs asks for its node:$zombies"`, and `:61` `out=$(scripts/drbd_rig.sh mxfs 2>&1)`.
- The laps did go through batch_lap.py with the subreaper active. MXFS_BATCH_LAP_KILLTREE=0 is set in neither command (`summary.log:15` and `:17`). The holders are observed in state Z, which cannot happen without the subreaper: init would have reaped them at once (`tests/drbd_zombie_holder_lap.sh:21-23`).

The probe samples the holder's state before mxfs runs, not at the instant lun_pool checks the owner. Two facts close that gap. First, batch_lap.py reaps nothing on the normal path until the lap ends (`:275`). Second, in all 10 control laps the refusal issued at mxfs's owner check names the same zombie PID the probe reported. So the zombie is shown to persist through that check on this exact lap. **Met.**
