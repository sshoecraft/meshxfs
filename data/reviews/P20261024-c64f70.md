## Check 3: both oopses are the same fault

- Code bytes: `:505` matches `netconsole.log:96152` byte for byte, including `41 8d 45 ff <4c> 8b 7f 10`. The faulting instruction is `mov 0x10(%rdi),%r15` with `RDI: 0000000000000000` (`:508`, `netconsole.log:96155`), which matches `CR2: 0000000000000010` (`:514`, `netconsole.log:96161`).
- Registers: RAX `000000000001ffff`, RBX `0`, RCX `1`, RDX `0000000000020000`, RSI `0`, RDI `0`, R08-R11 `0`, R13 `0000000000020000`, R14 `1` and R15 `0` match exactly (`:507-511` against `netconsole.log:96154-96158`). RSP, RBP and R12 are stack addresses and differ. FS, GS and CR3 are per-boot values and also differ.
- Call chain: `:517-536` matches `netconsole.log:96164-96183` frame for frame, with the same offsets (`__req_mod+0x269`, `drbd_request_endio+0x99`, `submit_bio_noacct+0x1a7`, `drbd_send_and_submit+0x25b`, `drbd_submit_bio+0x21f`, `__blkdev_direct_IO_async+0x1bb`, `blkdev_read_iter+0xf0`, `aio_read+0x13b`).

Same RIP, same instruction, same register state at the fault, same path. Confirmed. No MXFS frame is on either stack. Confirmed.

## Check 4: the proposal's claim that no rig script runs LVM against the DRBD device

The proposal says: "The rig's scripts run no LVM command against the DRBD device (the record's own search: only a comment at tools/lun_pool.sh:309)". I grepped `scripts/ tools/ tests/lib/ packaging/` for `lvm|pvscan|vgscan|vgchange|lvchange|pvcreate|vgcreate|lvcreate|pvs|vgs|lvs|...`. The claim, as written, is wrong:

- `tools/lun_pool.sh:309` reads `# umount tried).  Each umount is bounded: an unbounded one that hangs in the`. It is not an LVM line at all. The LVM comment in that file is at `:325-326` (`lvm2-monitor's stop then read the LUN through / the dead path`).
- `scripts/pve_lvm_drbd_baseline.sh:103` `on "${PAIR[0]}" "vgs $VG >/dev/null 2>&1 || { pvcreate -q /dev/drbd$MINOR && vgcreate -q $VG /dev/drbd$MINOR; }; vgs $VG" 60` and `:104` `on "${PAIR[1]}" "pvscan --cache >/dev/null 2>&1; vgs $VG" 60` run LVM directly against a DRBD device. Its targets are the PVE pair (`:34` default `192.168.1.80 192.168.1.81`), and `:7-8` says MXFS's own resource is "not touched". Those hosts do not run `6.8.0-101-generic #101-Ubuntu` on QEMU i440FX, so these lines are probably not the trigger on test18 or test1/test2. Still, they are in the tree, and the proposal's search did not report them.
- `tools/mxfs_revive_node.sh:145` `sudo vgchange -an ubuntu-vg` runs on the lab host against an nbd-attached image, not inside a guest. It is not relevant.

There is also an indirect path that the proposal never considers. MXFS's own package install retriggers udev on every block device:
- `packaging/mkdeb.sh:97` `udevadm trigger --subsystem-match=block 2>/dev/null || true`
- `packaging/mkrpm.sh:206` `udevadm trigger --subsystem-match=block 2>/dev/null || true`
- `packaging/install_source.sh:75` `udevadm trigger --subsystem-match=block 2>/dev/null || true`

A block change uevent on `/dev/drbd0` makes the distribution's lvm2 udev handling run `lvm` itself on that device. A task named `lvm`, rather than `vgchange` or `pvscan`, doing an O_DIRECT aio read is consistent with that. I am not saying this happened. I am saying the proposal's conclusion that "'lvm' is the guests' own lvm2 device scan" is reached by elimination, not measured, and the elimination is incomplete.

## Check 5: could MXFS still be causally involved in instance A in a way instance B does not exclude?

Yes. Instance B proves only that the mxfs kernel module is not needed to reach the NULL dereference once its precondition exists. That precondition is a backing bio failing inside its own submission (`submit_bio_noacct+0x1a7` -> `bio_endio`) while a direct read is in flight on the DRBD device. B does not show how that precondition arose, in either instance. Three things that can produce it, or the `lvm` read, survive `Not tainted`:

1. MXFS's userspace DRBD management runs without the module. `packaging/mxfs-drbd@.service:23` `ExecStart=/usr/sbin/mxfs-drbd-fence-self boot %i ${MOUNTPOINT}` and `:27` `ExecStop=/usr/sbin/mxfs-drbd-fence-self stop %i ${MOUNTPOINT}` bring the resource up, promote it and step it down. `packaging/mxfs-drbd-guard.service:11` `ExecStart=/usr/sbin/mxfs-drbd-fence-self guard`. `tools/mxfs_drbd_fence_self.py:833` `subprocess.Popen(["/bin/sh", "-c", "sleep 1; drbdadm disconnect %s; %s"` changes DRBD state from the fence path. In instance B the DRBD resource is MXFS's own (`:476` `drbd mxfs/0 drbd0: State change failed: Refusing to be Primary while peer is not outdated`), so MXFS tooling had configured that node's DRBD.
2. In instance A the module was loaded and starts userspace helpers that drive DRBD: `pal/linux/drbd.c:379` `rc = call_usermodehelper(argv[0], argv, envp, UMH_WAIT_EXEC);` and `:3227` (same). B, with no module, cannot exclude a precondition that this route produced in A.
3. The rig's own LUN pool removes DRBD's backing disk, which is exactly the record's precondition. `scripts/drbd_rig.sh:120-122` says: `rebind (tools/lun_pool.sh).  A fresh bind logs the node out of every target, / which pulls the disk out from under a running DRBD — so DRBD is always taken / down on both nodes before any allocation.` Instance B's node, test18, carries both a DRBD `mxfs` resource (`:457`, `:476-481`, `:489`) and a pool-LUN test's evidence (`reap_inactive_mount_ab`). Nothing in either cited file shows which of the rig's binds, if any, preceded either oops.

The record's own `next` set the bar this proposal had to meet: "establish what failed the backing bio in each (the pool LUN released under a live DRBD device, or a path loss), and whether lvm's scan of /dev/drbd0 is something the rig or the packages do; then this is either a DRBD driver fault reached by the rig with MXFS absent (remove --disproved on that direct evidence) or a sequence an MXFS install can produce, which keeps it open." The proposal answers neither question. It does not identify what failed the backing bio in either instance, and its answer on lvm is an inference built on an inaccurate search (Check 4).

## Verdict: REJECT

What is proven: the two oopses are the same fault in the stock in-tree `drbd` module (same RIP, instruction, registers and call chain). No MXFS frame is on either stack. Instance B's boot never had mxfs in the kernel (`Not tainted`, `:502`, and the module list at `:565`).

What is missing before this record can be removed as disproved:

1. **The precondition in instance A.** What failed the backing bio in its own submission at uptime 7834 s, with measured evidence (the node's initiator or target log, the rig's lun_pool bind and release log, or the run's DRBD state lines) that it was not an MXFS sequence: the module's usermode helpers, `mxfs-drbd-fence-self` (boot, stop, guard or fence-peer), or a rig pool bind or release under a live DRBD device. Instance B being on a different boot of a different node says nothing about how A got there.
2. **Who issued the `lvm` read.** Show that it was neither MXFS's packaging (`udevadm trigger --subsystem-match=block` at `packaging/mkdeb.sh:97`, `mkrpm.sh:206`, `install_source.sh:75`) nor an MXFS unit or rig step, for instance from the guest journal's `lvm[<pid>]` lines or udev logging around the event. Correct the search claim too: `tools/lun_pool.sh:309` is not an LVM line, and `scripts/pve_lvm_drbd_baseline.sh:103-104` does run `pvcreate`/`pvscan` on a DRBD device (on the PVE pair).
3. **Or the direct reproduction the record already names.** On a pair with no MXFS installed at all (no module, no mxfs userspace, no mxfs units, no mxfs udev rules), with DRBD up on a pool LUN: cut the backing path by non-MXFS means, run an O_DIRECT aio read of `/dev/drbd0` (`lvm pvscan --cache /dev/drbd0`), and capture the same `__drbd_change_sync+0x56` oops. That proves the crash is DRBD's response to a failed backing bio, independent of MXFS. If the precondition in A or B then turns out to come from a rig sequence, that is a harness defect to record and fix. It is not grounds to remove this record unproven.

"No mxfs module was loaded in another instance" removes one suspect. It is not direct evidence that the behaviour reported here, a node of MXFS's DRBD configuration crashing, could not have been produced by MXFS's own DRBD sequences.
