- Proposal: P20261024-56b663

## Check 1: reach comes from runs on the configuration, never from reading code

The standard for this kind: reach comes from runs on the configuration, never from reading
code. Narrowing needs measured evidence that a precondition of the defect is absent where
it is being excluded.

The proposal's own argument says where its reach came from: "Read from the code:
mxfs_pr_paths_get (pal/linux/kern.c:5772-5782) returns no path ...". Every step of the
argument is a reading of a source line or of the prose description of an attachment:

- `pal/linux/kern.c:5780-5782` --
  `if (!bdev || bdev_is_partition(bdev) ||` /
  `    strncmp(bdev->bd_disk->disk_name, "dm-", 3))` / `		return;`
- `pal/linux/kern.c:6823-6825` -- `mxfs_pr_paths_get(bdev, &t);` / `if (!t.n)` /
  `return 1;`
- `pal/linux/kern.c:7121-7124` -- `m = mxfs_pr_map_find(devt);` /
  `if (!m || m->key != key) {` / ... /
  `return 0;		/* not a map this node registered per path */`
- `data/configurations.json:49` -- `"doc": "each node's own initiator, one path: an
  in-guest iSCSI login to the rig's SCST target on one portal"`
- `data/configurations.json:70` -- `"doc": "the hypervisor's initiator; the disk is passed
  into the VM as a SCSI LUN"`

That is the code reading and the prose the standard excludes. None of the cited files is a
run. Nothing cited was measured on direct, direct4k or pass.

The precondition can be measured, and nobody has measured it. A per-path map is recorded at
mount only on the path that prints a log line:
`pal/linux/kern.c:6861-6862` -- `mxfs_pr_map_set(bdev->bd_dev, key, &t);` /
`pr_info("mxfs: P-PR-PATHS-REGISTERED %s key=0x%llx paths=%d registered=%d unreachable=%d\n",`.
A narrowing would need the mount kernel logs of named runs on each excluded attachment,
cited by CONFIG:ROW:ISO. Those logs would have to show what device the volume was mounted
on (not a `dm-` disk) and show that no `P-PR-PATHS-REGISTERED` line exists for that mount.
Because the plain-register path (`pal/linux/kern.c:7351-7381`) logs nothing on success,
the absence of that line is a negative. It would need a positive record of the device
alongside it, such as the mount line naming `sdX` or the rig's own device record for the
attachment. The proposal cites none of this.

Result: FAIL. The reach is inferred from code. It was not measured on the configuration.

## Check 2: the attachment descriptions are not evidence of what the rig ran

`data/configurations.json:48` -- `"device": "/dev/disk/by-path/ip-192.168.120.1:3260-iscsi-iqn.2026-05.local.mxfs:shared-lun-0",`
and `:69` -- `"device": "/dev/sda",`. These are the configured device names. They are not a
measurement of the block device that `mxfs_pr_paths_get` was handed in any run. Whether a
direct, direct4k or pass mount ever lands on a `dm-` disk depends on the host, for example
on whether dm-multipath claims a single-path SCSI disk. That is exactly what a run shows and
a description does not. The proposal names no run where it was observed.

Result: FAIL. The proposal offers prose as evidence for a property of the rig.

## Check 3: the cited ruling does not confine the hazard to multipath

`docs/rulings/silent-peer-death-under-the-stall-limit.md:300-303` --
`- **The late REGISTER is a fencing problem of its own.** A registration-creating command that`
/ `executes after PREEMPT AND ABORT puts the fenced key back on its nexus, and no later READ KEYS`
/ `can tell; SCSI keeps no tombstone of a removed key. Either registrations are created only while`
/ `the incarnation is not yet fenceable and reconnects only verify retained ones, ...`

The ruling states the hazard for any registration-creating command after the fence, and it
names reconnect handling. It does not say the hazard exists only on a dm-multipath map. The
proposal cites the ruling but quotes nothing from it that supports excluding direct,
direct4k or pass. The record is currently `observed 1/any`, a hazard read from the code with
no run. No run anywhere has shown its precondition present or absent: the record says "no
P-PR-PATH-FILL-LATE or P-PR-PATH-QUARANTINED line has been read from any rig log".

Result: FAIL. The ruling the proposal cites gives no support for the narrowing.

## Verdict: REJECT

The narrowing to `*/*/mpath` rests only on reading `pal/linux/kern.c` and the prose of
`data/configurations.json`. This decision kind requires measured evidence, from runs on the
excluded configurations, that the defect's precondition is absent there. The precondition
here is a per-path PR map recorded at mount.

Missing, and required before a resubmission can be approved:

1. Named runs (CONFIG:ROW:ISO, in their boards' ledgers) on each excluded attachment:
   direct, direct4k and pass, on each lock manager the narrowing would release.
2. From each run, the kernel log of every node's mount, showing the block device mounted
   (not a `dm-` disk) and showing that no `P-PR-PATHS-REGISTERED` line exists for that
   mount, cited by `file:line`.
3. Anything that shows the late-path fill never reaches its REGISTER on those attachments
   in a run that exercises path loss and recovery. A clean run alone does not count. It
   must be a run where the fill would have had a reason to act, so that its absence is
   measured rather than assumed.
