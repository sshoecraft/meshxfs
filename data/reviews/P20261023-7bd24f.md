## Verdict: REJECT

The proposal fails three of the remove --fixed conditions. (1) The fix-on batch has not passed: it is
still `open` in the queue, and the proposal says so itself. (2) The fix was never exercised on the
configuration where the defect was observed. The defect was seen on `8/disk/caw/mpath` and
`16/disk/caw/mpath`. Every lap ran the TCP branch (`force_transport=1`) and never ran the CAW branch
(`ft=0`, tests/mpath/lib.sh:521). (3) No lap measured the defect itself, which is a rejoined victim
running the wrong death window. The laps compare the text of an argv that a recorder captured. No
module was loaded and no `/sys/module/mxfs/parameters` value was read. The record's own next step
asks for exactly that read. The ledger rows also put the laps at `2/net/mesh/direct`, but the laps
ran `MXFS_CONFIG=8/net/mesh/mpath`.

## Check 3: the fix-on batch, sized from the control, passed every lap with exposure

Sizing: correct. For 10/10 at alpha=0.005, the lower bound is 0.005^(1/10) = 0.5887. The smallest N
with (1 - 0.5887)^N <= 0.005 is N = 6 (0.4113^6 = 0.0048; 0.4113^5 = 0.0118). This matches step10.log:1
`declared verification batch b20261023-abfebf ... 6 clean laps (rate 10/10, lower bound 0.5887, delta 0.005, alpha 0.005)`.
The batch was declared before lap 1 (step10.log:1 precedes :3).

Laps: step10.log:9 `verify b20261023-abfebf: 6 PASS, 0 FAIL of 6 planned`. The ledger rows
data/criteria.runs.jsonl:11041-11044 and :11046-11047 are all PASS with `exposure=1`. The probe is
present, for example batch_laps/b20261023-abfebf/20261023T204814Z-40edd902.log:11
`LAP rejoin_modargs INSMOD-LINE: insmod /root/mxfs.ko.prep force_transport=1 target_cache_protected=1 log_repeat_limit=0 dyndbg=+p dead_timeout_ms=12000;`

This check still fails, for three reasons.

**(a) The batch has not passed.**
- data/defects.json:5007 `"state": "open",`, which is the state of b20261023-abfebf (id at data/defects.json:4997).
- tools/defects.py:1752 `if fixon.get("kind") != "verify" or fixon.get("state") != "passed":`
- The proposal's own argument, item (9): "b20261023-abfebf is still 'open' in the queue; tools/defects.py remove --fixed requires it 'passed' (tools/defects.py:1752), which needs a verify proposal and defects.py verify first."

A removal cannot be approved on a verification batch that has not been reviewed and recorded as passed.

**(b) The configuration where the defect was observed was never exercised.**
- data/criteria.runs.jsonl:9699 `"config": "8/disk/caw/mpath"` (board_20261023T144020Z-g8_path_fence_degraded)
- data/criteria.runs.jsonl:9707 `"config": "16/disk/caw/mpath"` (board_20261023T144449Z-g16b_path_fence_degraded)
- The fix's CAW path is a separate branch: tests/mpath/lib.sh:521 `case " $rig " in *" force_transport=0 "*) ft=0 ;; *) ft=1 ;; esac`. prep's CAW arguments come from tests/setup/prep_node.sh:54 `caw) MODARGS="force_transport=0 target_cache_protected=1 log_repeat_limit=0 dyndbg=+p" ;;`.
- Every lap, control and verification, ran `MXFS_CONFIG=8/net/mesh/mpath` (summary.log:19 and :21), which takes `ft=1`.
- The proposal concedes this in item (8d): "the observed lanes were 8/disk/caw/mpath and 16-node CAW, and the CAW branch (lib.sh:521, ft=0) was not exercised."

The verification never ran the code path that runs where the defect occurred.

**(c) The verification never measured the defect.** The defect is a rejoined victim running
`dead_timeout_ms=0` while its peers run 12000. The lap compares text only:
- tests/rejoin_modargs_lap.sh:12-14 `# tests/mpath/lib.sh, with tests/lib/rig.sh, on this host, with no node touched:` / `# ssh ($SSH) and virsh ($VIRSH) are this script in its recorder mode.  The` / `# recorder writes down every command it is handed and runs none of them, except`
- tests/rejoin_modargs_lap.sh:101 `mapfile -t got < <(bash -c "printf '%s\n' $argtext")`
- The load never ran: batch_laps/b20261023-abfebf/20261023T204814Z-40edd902.log:6 `    ABORT: the rejoin of test14 (rejoin) produced an EMPTY capture (/tmp/tmp.ttHVekqFkT/out/rejoin_test14_rejoin.txt); nothing was measured`
- The record's own next step asks for a read of the loaded parameter (data/defects.json:4976, `next`): "The rejoin half: ... its lap reads the victim's /sys/module/mxfs/parameters inside the same row, right after the rejoin." No lap does this. The proposal's item (8a) says: "no node's /sys/module/mxfs/parameters/dead_timeout_ms was read after a rejoin".
- Other branches of the shipped command were not graded either:
  - Item (8b): the modprobe branch was printed but not compared (40edd902.log:12 `MODPROBE-LINE: else modprobe mxfs ... dead_timeout_ms=12000;`).
  - Item (8c): the contract quoting at tests/mpath/lib.sh:523 was not exercised. That argument is built as `'target_retire_contract=\"$c\"'` and expanded into an ssh command line. Whether it reaches insmod as one element was not tested.

Passing laps that compare a recorded command string are evidence that the string changed. They are
not evidence that a rejoined node now loads `dead_timeout_ms=12000`. "Testing that exercises the
cause" would load the module on a rejoined victim and read its parameters.

## What would make this approvable

   rejoins it through `pf_boot_rejoin` and reads `/sys/module/mxfs/parameters/dead_timeout_ms` (and

2. Ledger rows recorded at the configuration the lap actually ran.
3. A control with `PF_REJOIN_PREP_ARGS=0` on that lap, measured at its rate, and a verification
   batch sized from it that is declared, run, verified through its own reviewed verify proposal and
   in state `passed`.
4. Each branch the fix claims to cover, graded on its own: CAW, modprobe, and contract set. Or the
   claim narrowed to the branches that were graded.
