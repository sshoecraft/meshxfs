## 4. The fix-on laps never measured the max_stall_ms= path. NOT MET

The fix reads two sources: `max_stall_ms=` lines (STALL_LINE, which is always read) and declared
`--stall` patterns. The lap prints one stall in each form, 31000 ms as `max_stall_ms=` and 31500 ms
as `op_ms=` through `--stall`. stall_graded keeps only the maximum (:314) and appends that one value
(:317). The lap passes on that value alone:

- tests/batch_lap_stall_lap.py:120 `        if run.get("outcome") == "FAIL" and f"max_stall_ms={over_ms + 500}" in measured:`

The worst value 31500 can only come from the `--stall` match of `op 2 op_ms=31500`. Suppose the fix
did not read `max_stall_ms=` lines at all, for example through a broken STALL_LINE or a regression at
:311. The recorded run would still be `FAIL ... max_stall_ms=31500`, and all six verification laps
would pass unchanged. The fix-on result therefore shows only that the `--stall` path grades a recorded
run. It shows nothing about the `max_stall_ms=` path.

The earlier batches do not fill the gap:

- Verification b20261023-f16825 used the same harness with the same masking. Its laps read
  `graded FAIL: rc=0 elapsed_s=0 worst_ms=31500 ...` (data/reviews/P20261023-d6265d.md:64).
- The real ledgers hold no batch_lap.py run that carries the field. I ran this myself:
  `grep -h 'batchlap' data/criteria*.jsonl | grep -c 'max_stall_ms='` returned `0`, out of 1037
  batch_lap.py-recorded runs.

This is not a corner case. No lane has ever declared `--stall` (data/reviews/P20261023-8d639f.md:100).
The harnesses that report a stall do it in the `max_stall_ms=` form:

- tests/auth_suspend_lap.sh:126 `echo "max_stall_ms=$MAX_MS"`

offered for it is a reading of :311, which is inference, not measurement.
