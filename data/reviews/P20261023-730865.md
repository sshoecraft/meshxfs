## Verdict

**REJECT.**

The batches prove one thing well. With `iwr_ra_partial=0`, a rejoin's recovery writes a skipped directory's cluster whole and reverts a survivor's newer slot (10/10 at each configuration). With the shipped default of 1 it does not (6/6 at each, correctly sized).

What a fixed-and-verified removal also needs, and the proposal does not have, is instrumented proof that this mechanism caused the record's observed loss at 4/disk/caw/mpath:path_all_lost:2026-10-23T16:32:35Z:

1. The proposal's chain misreads the run. The next reader after test3's release was test5 (kmsg_test5:191187-191205, cc=8381), not test4. test5's last release before test4's read was 118 bytes at chg=8386 (kmsg_test5:191340), not 101 (:191180 is an earlier tenure). The 118-byte image test4 read is test5's image (it holds `test5.549.r`), not the one test6 wrote.
2. Read correctly, the run shows the cc=8381 image on the platter after test3's release. It does not show that test3's cc=8382 / 120-byte image was ever there first. That step rests on reading P146 `flushed=1 wrote=0 rerr=-11` and absent pr_debug probes through code from a different build (run 08D63764A9352FBDD5A76CD, source not available). The proposal concedes no clobber detector saw it. One alternative is not excluded: test3's release reported flushed=1 without its rename landing, and this fix would not touch that.

What would close it, any one of these:

- The source of build 08D63764A9352FBDD5A76CD, shown to match the candidate's xfs/xfs_mxfs_bast.c release loop (:1342-1652, :2200-2347) and its probe callsites, together with a corrected chain naming test5's read.
- A path_all_lost run (or a lap with a live, non-unmounting survivor) at 4/disk/caw/mpath with `dino_clobber_check=1` and `iwr_ra_partial=0`, whose `P-DINO-CLOBBER path=whole live_revert` on the shared directory's cluster shows the rejoin's write reverting a survivor's landed slot.
- Instrumented evidence in the run itself that test3's 120-byte image reached the platter before test6's write.
