What holds:
- Size: L = 0.005^(1/10) = 0.58870, and N = ceil(ln 0.005 / ln(1 - 0.58870)) = ceil(5.9636) = 6 (`tools/defects.py:918-926`, recomputed). `step8.log:1` `declared verification batch b20261023-cff97e ... 6 clean laps (rate 10/10, lower bound 0.5887, delta 0.005, alpha 0.005)` comes before its first lap at `:3`.

Each of the 6 lap logs has its `EXPOSED:` line. No lap failed and none was dropped.

What does not hold. The batch never ran the fix where the record puts the defect, so on that path the fix is inferred, not verified.

1. **No node, no mxfs mount, no /root.** Every lap log says `=== VMs held for the lap: none ===` (for example `b20261023-cff97e/20261023T204752Z-33031518.log:2`). The work directory was on the host's tmpfs: `tests/fsx_fail_files_lap.sh:43` `D=$(mktemp -d -p /dev/shm)`, `:51` `FSX_LOG_DIR="$LOGD" MXFS_NODES=1 timeout -k 5 "$BOUND" "$FSXSH" "$MNTD"`. The verbatim paths show the same: `...33031518.log:18` `fname = /dev/shm/tmp.brCUnZv5lP/mnt/.suite_fsx.clyde.3935981/fsxfile_100000`. The laps are booked under `2/net/mesh/direct`, but `summary.log:3-4` says only that `--at names the configuration each lap is recorded under` and that `No VM is touched`.
2. **The node path runs different code.** On a node the destination is the default `tests/suite/fsx.sh:46` `local base="${FSX_LOG_DIR:-/root}/fsx.$SEED.$1"`. I found nothing in `run.sh`, `tests/suite`, `tests/*.sh` or `tools` that sets `FSX_LOG_DIR`; the only hits are the comment at `fsx.sh:36` and the use at `:46`. So the deployed `mv -f` at `:54` moves files from the mxfs mount to the root filesystem, which is a read-copy-unlink. In every lap here it was a same-filesystem rename(2) inside one tmpfs. The proposal concedes this in its own section 7(a): "On a node the row moves the files from the mxfs mount to /root, a cross-filesystem copy and unlink by mv -f; that path never ran."
3. **That difference matters for this fix.** On a node the move runs right after fsx reported a fault. It has to read up to about 256 kB of `.fsxgood` back through an MXFS mount that has just miscompared. On tmpfs that read never happens. Whether it succeeds, returns an error (hidden by `2>/dev/null` at `:54`, visible only as a shorter `fsx_fail_kept=`), or stalls the row on a bad mount was not measured.
4. **The record's own measurement plan was not followed.** `data/defects.json:5950` asks for a lap that "lists what survives the row on the node". No lap ran on a node.

A removal closes the record for every configuration (`data/defects.json:5945-5946` `"nodes": 1,` `"config": "*/*/*",`). Its CHANGELOG entry is built from the summary above, which describes the mxfs mount and `/root`. The evidence verifies the fix only for a tmpfs-to-tmpfs rename on the lab host.

## Verdict: REJECT

The control reproduced the loss at 10 of 10, and the fix-on batch is the right size and passed 6 of 6 with exposure. But every lap ran on the lab host's tmpfs. No node, mxfs mount or `/root` destination was involved. The fix's move on the path the record describes, a cross-filesystem read-copy-unlink from the mxfs mount straight after a miscompare, never ran, and the proposal says so (section 7(a)). Calling it fixed there is inference. The verification batch is also still `open` with no verify verdict.

**What is missing:**
1. A verification batch, sized from this control (N = 6), that runs fsx.sh's own code on a rig node, with `$W` on the mxfs mount and the logs at the default `/root`. Each lap must show the exposure probe and list what survives the row on that node, with all three files of each failed check kept and `fsx_fail_kept=fsxlog,fsxops,fsxgood` in the result.
2. A control on the same path with the switch off, if the rate is to be taken from the node path rather than carried over from tmpfs.
3. The batch's verify verdict recorded and reviewed before the removal is proposed again.
