# Harness and oracle blind spots, rig operation traps, product traps found through rig work, and delete/delegation guard traps

Topic: running the MXFS lab rig and its harnesses without being fooled by them. Common shape: the arm, window, probe, clock, mount or command you believe is in force is not the one that ran, so a harness prints PASS/FAIL (or an investigation finds no cause) while the real failure is outside what it looked at, or a symptom that reads as a filesystem hang or refusal is really a local shell, a missing mount, a skewed clock or a host-keyed query. Also the delete/permission/delegation traps that surface when cleaning up after such runs. The user's standing process corrections and the lab-VM handling rules were split out to [[compiled-user-process-corrections-and-lab-vm-rules]] when this article passed the size ceiling. Folded into the original harness/oracle article: `compiled-user-process-corrections-and-rig-operating-traps` (twelve notes; all stand as written unless marked superseded), `compiled-pve-guest-lifecycle-delegation-scripts-and-rig-diagnosis-traps` (assorted; dated 2026-10-11 unless noted) and `compiled-multi-resource-drbd-fencing-and-multi-mount-harness-traps` (assorted; multi-mount DRBD work, 0.90.120/121). Backticked names ending a bullet (`trap-`, `feedback-`, `user-`, `technique-`) are the raw notes folded earlier, already deleted, kept as provenance.

## Harness and oracle blind spots

- Cleanup is part of the workload. `tests/pve_pair_write_bound.sh` captured and judged kernel logs, then `rm -rf`'d its files and printed PASS. Freeing large extents takes AG locks; on the physical DRBD pair the removal hit `DLM AG lock failed: ag=2 rc=-11` in `xfs_defer_finish_noroll` and pve2's mount shut down 1 s after PASS. Capture and judge logs AFTER cleanup and assert mounts are still live at the very end. When auditing a host, read the whole boot's log for P-WITHDRAW / `Shutting down filesystem`; auto-rejoin hides it. `trap-a-test-that-reads-the-kernel-log-before-its-cleanup-misses-the-failure-the-cleanup-causes`
- A death test's probe must go through state the victim held (same directory, same AG). `tests/multi_victim_containment.sh` first run (retired-code `8/tcp`, 2 victims) passed on own-file write probes and `chk_mxfs rc=0` while an AG was quarantined and every load cycle got EIO. Tells that were printed but unused: `cycles=8648` on one node vs ~490 on peers (an outlier is an early-returning error path until shown otherwise) and `recovered_lines=1` for two victims. `chk_mxfs` exits 0 with a refused, quarantined slice, so a clean check is not proof of recovery. Load-loop exit codes must not go to /dev/null. Read every printed count against its expected value before reading the verdict. `trap-a-death-harness-whose-probe-shares-nothing-with-the-victims-passes-while-every-shared-operation-is-refused`
- A verdict that counts a probe line must read that line's reason fields and its time. The same harness failed a lap on 10 `P240-QUAR-NSOP-REFUSE` lines at +7 s, before any kill, with `comm=find incarn_stale=1 rblk=0 quar_flag=0 quar_map=0` (the harness's own load-confirm `find` racing a peer's rm/re-create, ESTALE from the stale-incarnation gate). Count only when `rblk`, `quar_flag` or `quar_map` is non-zero and only after the first kill; check `comm=` and offset from T0 before calling a FAIL a containment failure. `trap-a-verdict-that-counts-a-refusal-probe-line-without-reading-its-reason-fields-fails-a-lap-on-the-harness-own-find`
- Any abort after the load is launched must first touch `/tmp/mvc_load.stop` on every node and wait for `.done`. The `load never appeared` ABORT (`exit 2`) did not, so the next queued lap's re-prep ran beside the survivor loops on the same `/mnt/shared/.mvc_load/nodeN` and shared `/tmp/mvc_load.{err,cycles,done}`: ENOENT/rm rc=1, `cycles=17407`, a 185 s fake stall, unmountable survivors, lap FAIL, no FS fault. Recognise it by two cycle numberings in one node's FAILED lines or a `.done` count far above ~300-350. A lap after an ABORT is suspect. Never edit the harness while a queued lap runs; bash reads the script lazily and each lap re-reads it. `trap-a-lap-that-aborts-after-starting-its-load-leaves-the-load-loops-running-into-the-next-lap`
- A module parameter set on the live mount is reset to its default by the lap's own rmmod+insmod. `agmeta_shutdown_retire.sh` set `ifree_eager_durable` before the churn, then reloaded the module; the closing `rm -rf` (the operation under test) ran at 0, and ten laps were written up as a false negative. "Read back = 1" proves the write landed, not that it was in force when the operation ran. Put a knob that must span a reload on the insmod line (`MXFS_EXTRA_INSMOD_PARAMS`, together with `MXFS_PRECHURN_KNOBS`). Pick the unconditional probe as proof; a probe gated on a threshold (`P137-IFREE-TIME`, only above 10 ms) reading zero proves nothing. An operation outside every dmesg window is unfalsifiable; the closing free now opens its own marker and emits `CLOSINGFREE-MEASURE`. Also: `mxfs_ifree_eager_durable` is not a publication guarantee; its AIL drain is bounded by `mxfs_ifree_drain_ms` (200) and only warns `P-IFREE-DRAIN-BOUND` on expiry (`xfs_inode.c:5108-5113`). `trap-a-knob-set-before-the-churn-is-gone-by-the-rmmod-insmod-later-in-the-same-lap`
- Before calling a path-row stall an MXFS fault, check the node clock. Two-load rows start/stop all loads together, so each pair of `load_<node>/ops.log` must span the same duration within ~1 s; constant offset at both ends is skew, differing start/end offsets is a mid-row step. Seen: test2 74 s behind made four rows FAIL on fake "72 s stalls" (disposed D-2NODE-MPATH-VICTIM-LOAD-BLOCKED-OUTSIDE-ITS-OPS as DISPROVED); a 366 s step made a 16.7 s op look like 383 s. pathload writes an op line only after the op returns, so gaps between ops are time outside MXFS. Harness fix 0.90.122: `tests/lib/rig.sh` `clock_measure`/`clock_off`/`clock_steady`; a node moving >2 s mid-row ends the row ABORT. Related: unmount rc=32 within ms is EBUSY; look for a stray pathload from an externally stopped chain. `trap-a-node-clock-offset-or-step-reads-as-a-filesystem-stall-in-path-rows` `compiled-pve-guest-lifecycle-delegation-scripts-and-rig-diagnosis-traps`

## Rig operation traps (the symptom reads as a filesystem fault, the cause is local)

- A rebooted rig node has no `/src`, so `prep_node.sh` silently does not run. It mounts /src itself but is read from /src; on a freshly booted node bash fails with ENOENT on stderr and a caller grepping NODE_PREP_(OK|FAIL) sees nothing. Later steps fail MOUNT_RC=32 because the module never loaded, which looks like a filesystem refusal. Fix in the caller before running anything from /src on a restarted node: `mkdir -p /src; mountpoint -q /src || mount -t nfs -o rw,vers=4.1,hard,timeo=600,retrans=2,tcp 192.168.120.1:/src /src`. An empty capture from a node step is a capture failure, never a filesystem verdict. Found during the multi-mount DRBD bring-up (0.90.120/121). `trap-a-rig-node-just-rebooted-has-no-nfs-src-so-prep-node-silently-does-not-run` `compiled-multi-resource-drbd-fencing-and-multi-mount-harness-traps`
- Bare `wait` in a harness that does `exec > >(tee log)` waits on the tee for ever. Bash 5.1+ counts the process substitution as a child; argument-less `wait` waits on the tee, which never exits. Writers finished in 0.6 s, the run sat for an hour and looked like an FS hang. Fix: `pids+=($!)` per job and `wait "${pids[@]}"`. Before diagnosing a harness "hang", check whether the remote work finished (files present, no D-state task); if so the hang is local. `trap-bare-wait-in-a-harness-that-tees-its-own-log-waits-on-the-tee-for-ever` `compiled-multi-resource-drbd-fencing-and-multi-mount-harness-traps`
- `mountpoint -q` stats the mount root; with the backing LUN gone it gets EIO and reports "not mounted" while `/proc/mounts` still lists it. `tools/lun_pool.sh` NODE_UNMOUNT broke out on that, never called `umount`, and every bind failed UNMOUNT_FAIL (test8-16, 0.90.123); plain `umount` succeeded instantly. Decide "still mounted" from `/proc/mounts`; use `mountpoint -q` only to gate `fuser -km` (on a non-mountpoint fuser resolves to `/` and kills sshd). A D-state `mxfs-worker bast_poll_fn` in msleep on such a node is not a stuck umount. `trap-mountpoint-q-is-false-on-a-mount-whose-storage-is-gone` `compiled-pve-guest-lifecycle-delegation-scripts-and-rig-diagnosis-traps`
- Scratch-copy build chained `rsync … && cd "$B" && t0=…; make modules`: rsync exited 23 (root-owned `bench.json` and `.xfs_fio_baseline.tcp.scst-fio.json` left by a sudo'd bench), the `cd` was skipped, and the `;` let make rebuild the TREE's `mxfs.ko` mid-queue; one verification chain straddled two srcversions. Fixes: `make -C "$B" modules` or `( cd "$B" || exit 1; make … )`; gate on rsync (`|| { echo rc=$?; exit 1; }`, 23 is not success); `sudo -n chown steve:steve` root-owned leftovers; no command may write the tree's `mxfs.ko` while a queue is deploying it. `trap-a-scratch-copy-build-chained-with-and-and-after-rsync-falls-through-to-the-tree-when-rsync-exits-23` `compiled-user-process-corrections-and-rig-operating-traps`
- A `run_in_background` Bash task (and any `run.sh` under it) is killed when ccloop relays the session; the in-flight board row finalizes ABORTED and the crash-test victim is left shut off. Launch any rig chain longer than one turn as `nohup setsid <cmd> > tests/evidence/<log> 2>&1 < /dev/null &` (as `tests/lap_queue.sh` is). It counts zero toward the Stop gate, so keep working in the foreground. Before believing a handoff that says a chain is running, check the log tail and `/proc/<pid>/comm` for the pid in `/tmp/mxfs_run.lock`. After a killed board, start the VM and force a fresh prep. `trap-a-background-bash-task-dies-with-the-session-at-a-ccloop-relay-so-a-rig-chain-must-be-nohup-setsid` `compiled-user-process-corrections-and-rig-operating-traps`
- Killing a full_verify/packaged_round process group kills only local ssh clients; remote `apt-get install` of the mxfs .deb (postinst DKMS build) keeps running on every node. Rerun then fails on the dpkg lock in 10 s, POWER=1 powers off mid-DKMS, and `dpkg --audit` shows mxfs "half-configured" on all nodes. Before rerunning: power the set up; on every node check `dpkg --audit` (or `rpm -qa`/`dnf history`), apt/dpkg processes, `dkms status mxfs`; `apt-get -y purge mxfs` a half-configured package and confirm nothing remains. Never edit a script (packaged_round.sh, tcp_peer_freeze_death.sh, lun_pool.sh) that a running full_verify may still read; each step is a fresh bash reading from disk. `trap-stopping-a-platform-round-leaves-its-remote-install-running-and-the-next-power-off-half-configures-the-package` `compiled-user-process-corrections-and-rig-operating-traps`

## Multi-node and multi-resource product traps found through rig work

- A per-host answer to a per-resource question in DRBD fencing strands every resource but the first (0.90.121; surfaced bringing up multi-mount / two-resource DRBD, resources mxfs and mxfs2, and the `tests/multi_mount.sh` crash arm). `trap-a-per-host-answer-in-per-resource-drbd-fencing-strands-every-resource-but-the-first` `compiled-multi-resource-drbd-fencing-and-multi-mount-harness-traps`
  - `mxfs-drbd-fence-self` excludes a dead peer once per resource, each under a fresh episode. `status <peer>` returned the first inhibit naming that host, so every other resource's witness saw AUTH_INHIBIT (another resource's episode) != its own RECEIPT_EPISODE. `dlm/drbdfence.c peer_fenced()` refuses on mismatch: `P238-DRBD-FENCE-NOT-YET` forever, recovery_pending=1, mkdir/ls/pvestatd in D state. The first resource recovers, so a one-filesystem check reads green.
  - Fix: `status <target> <resource>`; the witness passes its resource when agent=self. Node-fence authorities (ssh/exec, tools/rig_fence_virsh.sh) hold the HOST under one episode and reuse it for the second resource, so they stay per host.
  - Lesson: when adding multi-resource support, audit every query keyed by HOST where the producer keys by RESOURCE (episode files, nft tables, receipts). Test host death with BOTH mounted, not just mount/IO.
  - Confirm: on the stuck survivor run `/usr/sbin/mxfs_drbd_witness.py 0123456789abcdef monitor <minor>` per minor, compare RECEIPT_EPISODE vs AUTH_INHIBIT. Hot-installing the fixed witness/authority unblocked recovery in 15 s.
  - Side notes: `scripts/pve_mxfs_spare_disk.sh` only starts its unit (reboot tests need `systemctl enable mxfs-drbd@<res>`); `scripts/pve_pair_update.sh` used to stop only RES before rmmod.
- On a multi-node mount `xfs_inode_mark_reclaimable` runs `xfs_inactive` synchronously in the task dropping the last reference, and that takes the inode's DLM lock EX. So any `iput`/`xfs_irele`/`shrink_dcache_parent`/`d_prune_aliases` is a potential cross-node acquire. Doing one inside a directory acquire window (i_dlm_state ACQUIRING = 4, peer BASTs deferred) deadlocked against a peer in `rmdir` (child then parent): D-DIR-RELOAD-CHILD-INACTIVATION-DEADLOCK, 480 s, 15 nodes stuck at 0.90.122. Rule: never drop an inode reference inside an acquire window or under a held DLM grant; queue it (0.90.123 `i_mxfs_dshrink_work`). Signatures: P-ACQ-STUCK with unchanged hpr, P-DIRBAST state=4 ex=0 pr=0, P35-ACQBAST-HONOR in the same ms as the child lock returning; P-SYNC-INACT-SLOW (>=10 s) prints the caller stack, P-DSHRINK-INACT witnesses the deferred path. Cross-node timelines: map kmsg monotonic to wall clock via the median of (realms= minus mono ms), subtract the clock_test<N> offset; hpr=0x4000 is disklock slot 14. `trap-an-iput-inside-a-directory-acquire-runs-a-childs-synchronous-inactivation-under-the-held-grant` `compiled-pve-guest-lifecycle-delegation-scripts-and-rig-diagnosis-traps`

## Investigation and tooling

- Before shaping a reproducer for a rare board corruption, grep the run's own `tests/evidence/run_<row>_<id>/kernlog_test*.gz` for the inode numbers the audit named. For D-8TCP-RM-OF-A-CHILD that gave 289 lines and the whole chain (stale demoter claim, release by another task, commit at mode NL, write-fence restore, `P177-OBLIGATION-DROPPED-AT-ADOPT`) after 7+ stress laps had failed. Print tag plus key=value only (raw kernel lines trip the safeguard classifier); sort by node and second; dyndbg=+p means pr_debug tags are present. Count the precondition tag across all other runs of the board (it occurred once, in the corrupted wave). A stress shape that does not produce the precondition proves nothing; build a test-only injector, then control and fix arms on one build. `trap-a-rare-board-corruption-was-chased-with-stress-laps-while-the-board-had-kept-every-nodes-kernel-log-of-it`
- Calibrate an oracle on the host, not the rig: `tests/chk_oracle_calibration.sh` plus `tools/xfs_block_patch.py` on a `/var/tmp` 512M image via `sudo -n losetup` (mkfs_mxfs accepts block devices only, min 200 MiB). Patch one big-endian field and refresh the block CRC (crc32c 0x82F63B78; sb 0xE0, AGI 0x138, short btree 0x34) or you only prove CRCs are checked. Take geometry from the clean control's `chk_mxfs -v`; for bnobt patch both startblock and blockcount. Execution fixtures: missing path, zeroed sector 0, truncated image (rc 4), `timeout 0.01` (rc 124), SIGSEGV issued inside the root shell that spawned the checker (a 50 ms `timeout -s SEGV` outlived a 10-50 ms check; unprivileged kill of a root process fails silently). Gaps exposed: no detector for a dinode home aliasing a directory block; no offline two-level inobt constructor. `technique-calibrate-an-offline-checker-on-the-host-with-a-loop-device-image-and-crc-refreshed-field-patches-not-on-the-rig`
- A line-count-preserving rewrite must match horizontal whitespace only (`[ \t]*`, never `\s`). `scripts/strip_process_notes.py` used `\s*` after a session tag; at line end it ate the newline, the line-count guard silently kept the original, and 616 tags survived a CHANGELOG that said they were removed. Measure what is left across the tree, not files reported changed, and inspect leftovers (some were dead pointers). `trap-a-regex-that-can-eat-a-newline-silently-skips-a-line-count-preserving-comment-edit`

## Deleting things: permissions, ownership, delegation

- The settings deny `Bash(rm -rf /*)` is a glob: it denies `rm -rf` on every absolute path, including a literal scratchpad dir. No prompt, just denial. Workaround: `cd <scratchpad> && rm -rf <relative names>` in one call. The leftover trees came from `tools/scratch_build.sh` copying ~600-700 MB per version onto clyde's root ext4 and never removing it; eleven of them (15 G) caused the 88% preflight refusal. Remove the scratch tree after the FROZEN line lands. `trap-settings-deny-rm-rf-slash-star-blocks-every-absolute-path-rm`
- Same deny, another face: `rm -rf /home/steve/vms/qemu/<dir>` was denied twice; removing each image by exact relative path from inside the directory, then `rmdir`, was allowed. Rule from the user: resources a session created and then retires (VMs, images, LUNs, DHCP reservations, lab-file lines) are deleted in the same change, never left "for the user to decide". Mechanics: `virsh -c qemu:///system undefine <d> --nvram` (check `domstate` shut off), `sudo -n sed -i` the `dhcp-host=` lines out of `/etc/dnsmasq.d/lab.conf` (backup outside dnsmasq.d, `dnsmasq --test`, restart), trim `~/.config/mxfslab/lab` and `data/platforms.json` verify_env via `tools/platforms.py set --verify-env`. `feedback-resources-a-session-shrinks-out-of-use-it-deletes-itself`
- `/src` is NFS exported anon=root; root ownership there (dist/, tests/evidence/, build-container output) is a mapping artefact, never a reason a file cannot be removed. When a delete is refused, name what refused it (permission rule, hook) and hand over the exact command. Background: `infra-src-mxfs-is-nfs-root-squash`. `feedback-src-is-nfs-anon-root-so-root-owned-files-there-are-not-a-permission-problem`
- A delegation brief that lists forbidden commands leaves everything else allowed: a read-only `scout` brief banning pgrep/find//make/git still produced `rm -rf /src/mxfs/*.mk`, stopped only by luck (empty glob plus the shape check). Ban the class: no `rm`, `mv`, `cp`, `>` into the tree, `truncate`, `sed -i`, `install`, `chmod`, `chown`; keep the specific hazards as additions, and embed it in the agent definition. `trap-a-subagent-brief-that-forbids-the-known-hazards-still-permits-rm-name-the-whole-write-ban`
- A grind agent given prose steps improvised `xargs -0 -P4 -I{} bash -c '...'`; Claude Code cannot parse a `bash -c` body and stopped on a permission prompt (same for a `timeout 300 bash -c '...'` sweep). User: "Don't do this again. Write a script." (2026-10-11). `feedback-a-delegated-shell-pipeline-goes-in-a-repo-script-never-an-inline-bash-c` `compiled-pve-guest-lifecycle-delegation-scripts-and-rig-diagnosis-traps`
  - Multi-step or parallel shell work goes into a script in `tools/` or `tests/` first (example: `tools/compress_evidence.py`), then the agent runs that one script.
  - The agent prompt names the exact script and explicitly forbids `bash -c` / `sh -c` / `xargs ... sh -c`.
  - Data one-offs: `python3 - <<'EOF'` heredocs pass the checker; `bash -c` does not.
