Traps where the rig or harness produced a well-formed result about something other than the thing under test: another device, another target, a run that never started, a refusal that proves nothing, a bound or knob that does not mean what its name says. Folds in `compiled-priorities-defect-standard-and-rig-harness-measurement-traps` (12 notes: the User priorities and Rig and lab directives sections, plus the suite-binds-sda, DONE-gate, poll-sleep-bound, lap-grading and shared-injector items, each placed under the failure mode it belongs to). Every item cites its source note. The standing user priorities, the rig and lab directives and the product and target traps from that fold now live in `compiled-user-priorities-rig-lab-directives-and-product-target-traps` (split off to stay under the article size ceiling).

## Measured the wrong object

- **Wrong platter.** 34 harnesses read the LUN from `/home/steve/disk.img`, the image of the earlier SCST rig. On the QNAP rig nothing on clyde backs the LUN, so `chk_mxfs -v`, `mxfs_agi_dump.py`, `mxfs_logslice.py` and `--free-query` were valid measurements of another filesystem, printed as verdicts on MXFS. Fix: `data/rigs.json[<tag>].host_image` declares the backing file (`null` for the QNAP). `tools/mxfs_host_image.sh` / `mxfs_host_image` in `tests/lib/rig.sh` verify the envelope fsid against the LUN's before returning a path. `MXFS_HOST_IMAGE_PATH` overrides the path but never the identity check. With no host image, read from a node: `mxfs_chk_on_node` on an unmounted node (an rc-4 "held open exclusively" refusal means the wrong node, abort), or `chk_mxfs --query-only --free-query` on a mounted one. `technique-a-host-side-platter-read-is-a-rig-declaration-verified-by-fsid-and-the-qnap-lun-has-none`
- **Wrong target.** `/src/scst` is the old rig's target. The 2/tcp rig's LUN is a closed-source QNAP TS-453 Pro (`host_image: null`; the nodes' dmesg says `QNAP iSCSI Storage`; preflight reports "SCST not loaded"). Arguments from SCST source, such as the PR IN/OUT `dev_pr_mutex` ordering, and the "SA 0x05 blocks 12.3 s, victim write lands 126 us before PR completion" figures in `pal/linux/kern.c`, are SCST background, not a contract for the appliance. Target-instrumenting experiments (`tests/fence_inflight/inflight_ab.sh` with dm-delay and an ftrace probe on the target) cannot run against it. Measure from the initiators, or use a target-enforced primitive. An appliance result is a qualified contract and must be requalified when target, firmware or session topology changes. `trap-the-shipping-target-is-a-closed-source-appliance-and-src-scst-is-a-different-rigs-target`
- **Wrong LUN on a node in two sets.** test3 and test4 were rig nodes and also the ubuntu2404 platform pair, so each logged into two SCST targets. After a power cycle the iSCSI sessions came up in the other order: the 64 GB platform LUN was `/dev/sda`, the 128 GB rig LUN `/dev/sdb`. `run.sh` passed `MXFS_DEV=/dev/sda` to all nodes and test3 mounted the platform LUN alone. The only symptom was "cluster did NOT converge to 4 members within 110s" with test3 at `active_count=1`. Multicast was suspected and was innocent. The instrument that settled it was `/sys/block/sd*/device/wwid`. Fix: `run.sh` reads the formatted LUN's fsid and wwid on node 1 (`tests/setup/dev_identity.sh`) and ships `MXFS_FSID`/`MXFS_LUN_WWID`. `prep_node.sh` rebinds `MXFS_DEV` to the matching device (`DEVICE-REBOUND:`) or refuses. `scst_platform_targets.sh setup` now removes initiators that left a set. Rig nodes must never be in a platform set (ubuntu2404 moved to test5-8). A device path is a locator, never an identity. `trap-a-node-in-two-verification-sets-orders-its-luns-by-session-so-a-device-path-can-name-the-other-set-lun`
- **Wrong LUN: the 2/tcp suite's default `/dev/sda` is the LIO bench target.** The suite's `run.sh` defaults `DEV=/dev/sda`, which on test1/test2 is the LIO bench LUN on test32, not the real rig LUN, so suite runs silently measured LIO. LIO deadlocked on PREEMPT AND ABORT of a destroyed node (`core_scsi3_pro_preempt` -> `core_tmr_lun_reset` -> `target_put_cmd_and_wait`) and served no initiator; MXFS on the survivor behaved per design (PROUT-ABORT-FAIL, FENCE-BLOCKED-AMBIGUOUS, HB-STALL, SELF-FENCE, bounded withdrawal), and the lap failed as crash_audit. Run 2/tcp verdicts with `MXFS_RIG_TAG` and `MXFS_DEV` pointing at the real LUN by id. When a death lap fails with the survivor self-fenced, read the target's kernel (test32 dmesg, D-state stacks) before any MXFS hypothesis. `hostload` is clyde's load and may come from the user's own jobs, not the rig. `trap-the-2tcp-suite-binds-sda-which-is-the-lio-bench-target-and-lio-deadlocks-on-preempt-abort`

## A run that never ran reads green

- **Standing board read-back.** Host preflight aborted all six release boards (`run.sh` rc=3, pool filesystem 88% against a <88% gate). `tools/criteria.py` printed the STANDING board, still holding the previous release's rows, and `board()` in `tests/board_4node_chain.sh` graded only that read-back: "31 PASS". The tell was wall time, 14 s against ~27 min. Fix: `board()` returns 1 when `run.sh`'s own rc is non-zero. A chain step's wall time is evidence, so read the board log before believing "every criterion green". The host filesystem carries pool LUNs, guest images and user caches, so it creeps over the gate between runs. The pool tool's `destroy <number>` on a free LUN is the project-owned lever. `trap-a-board-chain-read-back-shows-the-standing-board-so-a-run-sh-that-never-started-reads-green`
- **Fence-row stacking.** Six chains of path_fence_degraded, path_fenced_return, path_all_lost and path_peer_withdrawn ran at once (g2, g2b, g4, g4b, g8, g8b). SCST logs one `scst_set_cmd_error_status ... Reservation conflict` line per refused command and a fenced node retries tens of times per second. Preflight refused lap starts ("~85 lines/s (max 40)", `run.sh` rc=3), and 9 of 11 g8 stages never ran yet the chain read the standing board. One wedged 8-node cluster (test9, UNMOUNT_FAIL, still sending I/O) logged 1607 conflict lines in a minute and `mxfs-clyde-guard` halted the rig (`.rig_halt`, reason FLOOD, 60 lines/s for 60 s). After any chain, run `grep -c 'clyde_preflight: FAIL' board_*<label>*.log` and check for `rc=3` before reading a row. Stack at most two or three fence-row chains. A node hammering a LUN it is fenced from is itself a finding. Never widen the preflight or guard thresholds. `trap-several-fence-rows-side-by-side-flood-the-host-kernel-log-with-scst-reservation-conflicts`
- **Editing a running script.** bash reads a script incrementally by file offset. Function bodies already parsed are safe, but every later top-level command is re-read from the saved offset, so inserting or deleting bytes above it makes the running instance execute mid-line garbage. Never edit `run.sh` or any `tests/*.sh` while a chain has it in flight (a chain parked in a gate loop counts as in flight, see the next item); queue the edit until DONE. If one already landed, revert it byte-identically before the current compound command ends. Pending at that time: the kill-time phase capture used `pkill -f '$script'`, which matches the remote shell's own `bash -c` line and kills it before `dmesg | grep mxfs-CCph > /tmp/ccph_last` runs, leaving every `testN.ccph` as a bare newline. The fix is the bracketed first character, `pkill -f -- '[${script:0:1}]${script:1}'`, on the node side only. `trap-never-edit-a-bash-script-while-it-is-running-run-sh-offset-shift`
- **DONE is not "rig free".** The rig's real resource is `/tmp/mxfs_run.lock`. Four chains gated on a log's DONE line woke together (plus a stale parked chain from the previous session): one won the lock, two burned a launch to a one-second FAIL, and one started `make modules` in the tree while the winner's preps insmod'd `mxfs.ko`, which would have split srcversion across the fleet mid-board. Rules: wait on the lock via `tests/rig_wait_free.sh` (walks `/proc/*/fd` and `comm`, never `pgrep -f`/`ps aux`); sequence stages in one process instead of fanning out chains; a build is a rig operation and is exclusive with any run. Second-order, same bash byte-offset mechanism as above: editing a script while an instance is parked in its gate loop corrupts it and the instance ran detached from its logging. Check `/proc/*/cmdline` for that exact filename before editing; a parked script counts as running. Caution added at compaction: `cmdline` reads take each task's `mmap_lock`, so on a host where any task may be wedged use `tools/mxfs_pgrep.sh` (skips D-state tasks first) for that check. `trap-done-gate-is-not-rig-free-run-lock-is-the-real-resource`

## A verdict that cannot distinguish its hypotheses

- **Refusal arm without a control arm.** The absent-SARK PREEMPT AND ABORT probe got RESERVATION CONFLICT, the wanted answer. But a refusal is the default outcome of any malformed command (wrong key, wrong type, wrong device, a CDB built differently from the kernel's). Fix: a third arm in the same lap, identical in key, `prout-type`, device and tool except that the service-action key is present, which MUST be accepted. It is asserted as a requirement (`rc=0`, generation advanced `0x175f -> 0x1760`), never logged for information. The mirror holds too: an "accepted" verdict needs an arm that must be refused. Read the PR generation on both sides of every command, not just the status; both refusal arms held it at `0x175e`. `technique-a-refusal-arm-means-nothing-without-a-control-arm-in-the-same-lap-that-must-be-accepted`
- **Injected fault never cleared.** `dbg_cert_fail_n=99` fails every certificate CAS, not just the publication window's, so the arm's second half (the peer gets its filesystem back) became unreachable. Four laps read as a product failure. The tell was `left=64` in the injector's own line at lap end. A fault that models a transient must be cleared where the transient ends. `trap-a-survivors-own-exclusive-write-gate-locks-the-victim-out-of-the-heartbeat-that-would-prove-it-dead`
- **A lap that asserts the absence of a behaviour the module declares grades the inverse of the design.** The network-partition arm held the DLM link down 120 s and required zero fence certificates, but the module's `tcp_death_grace_ms` is 40000, so a fence was the correct and guaranteed outcome and a textbook-correct resolution scored three FAILs. Read the module's own declared parameter at run time and grade against it; never hard-code the expectation in the harness. Grade on the observed outcome and let the declared bound decide which outcomes are allowed: inside the grace nobody may be fenced, past it exactly one side fences and owes the full chain (certificate, seal, slice replay, victim silent), and neither shape may produce two certificates. Near the grace (socket needs about 12 s to notice a block) either resolution is legitimate. `trap-a-lap-that-asserts-the-absence-of-a-behaviour-the-module-declares-it-will-perform-grades-the-inverse-of-the-design`
- **A shared debug injector cannot change meaning without re-reading every harness that arms it.** `dbg_auth_pump_pause_ms` skipped both the periodic gate call and the withdrawal pump, so one lap went VACUOUS three times (`reason=no-closure`). Moving the hold below the gate call would have fixed that lap and altered three others (`admitted_write_parked_across_fence.sh`, `auth_lease_resurrection.sh`, `fence_late_detection.sh`) that depend on the victim being blind. Before changing a knob, `grep -ln <knob> tests/*.sh` and read each use; a knob's semantics are part of every banked verdict. When a lap needs a different cut, add a second knob (`dbg_auth_withdraw_pause_ms`) and leave the first untouched. Name a knob for what it holds, not the thread it lives on. `trap-a-shared-debug-injector-cannot-change-meaning-without-re-reading-every-harness-that-arms-it`

## Boot-time dependencies that add wall time

- **Stale automatic iSCSI records.** A 0.89.84 2/tcp crash_audit failed at 241/300 s with every MXFS assertion passing. test1/test2 carried `node.startup=automatic` records for `iqn.2026-05.local.mxfs:shared` at 192.168.120.1/.2 (the SCST rig). With SCST down, `open-iscsi.service` took 2m02s and boot 2m31s, so the `timeout 240` expired while waiting for `/run/nologin`. Fix: `iscsiadm -m node -T iqn.2026-05.local.mxfs:shared -o update -n node.startup -v manual`; `scripts/mpath_up.sh` flips them back when it brings the multipath rig up. When a death/reboot lap overruns with MXFS checks passing, read the victim's `systemd-analyze blame` / `critical-chain` first. The packaged pair test3/test4's ~3 min reboot (blamed on lvm2-monitor) should be checked for the same cause. Related harness faults in `tests/packaged_round.sh`: `peer=` was given a hostname (the kernel needs a unicast IPv4 address) and the QNAP login was left `manual`, so the LUN did not return after the Proxmox reboot. `trap-stale-automatic-iscsi-node-records-add-two-minutes-to-a-rig-victims-boot`
  Same kind of record on the rig guests test5+: they log in at boot to an absent target, so boot waits about 2 minutes and `/run/nologin` can persist; root ssh works first. `trap-test4r-and-test5r-are-mac-clones-of-test4-and-test5-booting-one-takes-the-live-nodes-address`
- **/src NFS must not be an fstab auto-mount on guests.** `/src` is QNAP NFS (192.168.1.4:/src); an fstab entry with `defaults` is a hard mount, so an unreachable QNAP hangs or delays VM boot indefinitely (user, 2026-07-05). Mount it only in the buildup/prep step (`tools/prep_node.sh`, `tools/prep_tcm_node_scst.sh`, `ENSURE_NFS` in `tests/criteria/lib.sh`) and remove the fstab line, keeping the fleet consistent (it was split ~16/32). Never touch clyde's NFS exports. `feedback-src-nfs-not-fstab-automount`

## Checklist distilled

1. Before trusting a measurement, confirm which device, filesystem and target it touched (fsid, wwid, rigs.json), not which path; the 2/tcp suite's default `DEV=/dev/sda` is not the rig LUN.
2. Before trusting a green, confirm the run started: run.sh rc, wall time against budget, `clyde_preflight: FAIL` count, and that the rig was free (`/tmp/mxfs_run.lock`), not merely that a DONE line printed.
3. Before trusting a refusal, point to the control arm that must be accepted in the same lap. Grade a lap against the module's declared parameter (`tcp_death_grace_ms`), never a hard-coded expectation.
4. Before blaming MXFS for a slow or failed lap, read the victim's boot critical-chain and the target's own log (for the LIO bench target: test32 dmesg and D-state stacks).
5. Never edit a script a live chain is executing (a parked one counts); never widen a preflight, guard or timeout threshold to get laps through.
6. Before changing a debug knob, `grep -ln <knob> tests/*.sh` and read each use; add a second knob rather than altering the first.
