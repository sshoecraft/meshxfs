# Instrument, build and harness traps: a measurement that cannot see the thing reads as a finding

Assorted group: the clusterer could not fit these to one topic; two assorted articles merged. What they share is that an instrument, probe, pipeline, build or harness step produced a confident null, a green, a false FAIL, or a refusal that looks like a different cause than the real one. Sections 1-5 are instruments, probes and pipelines; sections 6-9 come from `compiled-build-tauth-tests-and-harness-measurement-traps` (how builds and test harnesses in MXFS report green or zero without having tested or measured anything: build mechanics, a source-location directive, harness/oracle assumptions that turn a harness defect into an apparent MXFS result, and one design-review lesson about guards in shared helpers). Organised by failure family.

## 1. A counter that measures something adjacent to the question

- `chk_mxfs -v <dev>` "Superblock icount" reads the platter superblock, which MXFS writes only at unmount (`sb_icount`, `sb_ifree`, `sb_fdblocks` are lazy; recomputed from AGF/AGI at mount; `sync` does not push them). Three live samples all said 64 while the run carved 187 chunks; the cold read after both unmounts said 12032. A live-mount superblock counter is historical: never gate a verdict on it, never subtract two of them. Gate on a number the workload produced (files created) or on the cold read. Same family: `df --output=itotal` reports `maxicount`, and `P133-ICLUSTER-SYNCINIT` / `P45-INIT` are print budgets, not counts. Ask what writes a counter and when. `trap-chk-mxfs-superblock-icount-lags-a-live-mount-by-one-unmount`
- A `pr_warn_ratelimited` count that lands exactly on 10 is `DEFAULT_RATELIMIT_BURST` (10 per 5 s), not a count. A 24-vs-10 gap between a plain and a ratelimited probe nearly became a false "persistent poison flag carried across laps" escalation. Never take a ratio between a ratelimited and an unratelimited probe. Use `static atomic_t n; if (atomic_inc_return(&n) <= CAP)` so printing is capped while the counter keeps the true total, and print the total. Comparing separate ratelimited call sites against each other is sound (independent state); the absolute count from one site is not. The same session also had a probe comparing fields that never move for the defect, and a harness grep for `[PASS]` against a bare leading word that recorded a genuine reproduction as `NO_TERMINAL_RECORD`. `trap-a-ratelimited-pr-warn-count-is-not-a-measurement-burst-is-10-per-5s`

## 2. A probe that exists but cannot fire on your path

- A probe guarded by the complement of its enclosing branch is dead code that reads as coverage: the chunk-delete branch in `xfs_difree_inobt` was entered under `!D || S` (not multi-node) and the `P103-CHUNKFREE` probe inside required `D && !S`. Every chunk deletion was silent. Check: conjoin the probe guard with every enclosing guard; if unsatisfiable, silence means nothing. A probe that has never appeared in any captured evidence though the path plausibly runs is a candidate; grep the evidence tree for the tag before believing a zero. `trap-a-probe-whose-condition-is-the-complement-of-its-branch-never-fires`
- "The probe exists" is not "the probe covers your path": `P132-CREATE` started its clock under `is_dir`, so file creates (every workload that sets the create ceiling) had no decomposition for ~350 sessions. Before believing a coverage claim, read: (1) the gate on the clock, not just on the print; (2) the threshold (`P138-ACQ` fires only above 5 ms, so a uniform 3 ms path is silent, identical to "fast" and "not measured"); (3) the print cap (`P291-EXWIN` 20000, `P138-ACQ` 4000, so a long run's tail can vanish). An absent measurement and a zero measurement look the same: `tools/p132_attribute.py` refuses to print when no input carried the probe, and `tests/suite/lib.sh` separates `notrun=` from `failed=`. `trap-a-probe-exists-is-not-a-probe-that-covers-your-path-check-its-gate`
- Fixing a vacuous probe can invert the vacuity instead of removing it. `P165-AFFINE-STALE` fired on 229,444/229,444 lines (`d_time=0`); narrowing to `d_time && d_time != epoch` removed log volume but is blind to the named population: `d_time` has one writer (the `ret == 1` tail of coordinated validation in `mxfs_drevalidate`), the affine fast path returns before it, and the conjuncts selecting that exit are constant for a positive dentry's life, so an affine regular-file dentry holds `d_time == 0` forever. A recorded "zero here is the first real evidence" would have been a confident wrong negative. A probe fix is verified only by demonstrating the new predicate CAN fire on the population at risk: which population does the branch sample, can every predicate field take a discriminating value there, is each field's writer reachable from this path. Claim blindness, not impossibility: `d_time` belongs to the dentry object and `d_splice_alias`, negative-to-positive reincarnation and `d_move` can carry nonzero values, so "unsatisfiable" was an overstatement a reviewer could refute. When the field cannot see the risk, measure the thing itself: `mxfs.affine_audit_pct` (0.66.0, default 0) diverts a sampled fraction into the skipped coordinated validation and compares. `trap-fixing-a-vacuous-probe-can-invert-the-vacuity-not-remove-it`
- **A probe not in the built module is a guaranteed zero** (from `compiled-build-tauth-tests-and-harness-measurement-traps`). `tools/probe_audit.sh` compared 1594 source probes against `strings -a mxfs.ko`: 17 absent, 8 of them counted by 6 harnesses. Four ways a written probe misses the binary: unreachable after an early `return` (retired `mxfs_disklock_recovery_begin`); wired only into a false `#if` arm; a condition the compiler proves false (`if (0 && ...)`, never-assigned local, uncalled static); a file not in the Kbuild object list (`xfs/xfs_mxfs_dentry.c`). When reading finds nothing, go to the compiler: `make M=... x.i` vs `x.o`/`x.s` separates preprocessor from compiler. Use `--gate P-NAME` as a harness build precondition; extract probe names only from text after the first double quote. `technique-ask-the-built-module-which-probes-exist-before-trusting-any-harness-that-counts-one`

## 3. Harness and pipeline steps that destroy or fake evidence

- `grep -v authorized` as an ssh-banner filter also deletes kernel lines containing "unauthorized image(s)" (`P227-FR-ATOMIC-SKIP`), the one line naming the mechanism behind `refused=2`; an hour of code reading followed. Anchor the filter: `grep -av '^Unauthorized\|^Warning:\|^If you'`. Never filter pulled kernel logs by a bare substring that can occur in a kernel message (authorized, warning, error, failed). When a counter says N and the notices are absent, suspect the pipeline first: `grep -c` on the node with no filter. 22 sites across six scripts were switched. `trap-grep-v-authorized-deletes-unauthorized-image-kernel-lines`
- Unbound variable inside a conditional arm reads as a fencing regression (sess563, s583neg, 2026-09-09). `tests/tcp_death_replay.sh` documented a default for `MXFS_DEV` in its own Env header and never had one. All four uses sit inside conditional arms, so under `set -u` a direct invocation did not fail at the top; it died partway through the sole-survivor gate arm, at line 876, the one line that reads the target's PR state:

      tests/tcp_death_replay.sh: line 876: MXFS_DEV: unbound variable
        INFO PR state on test1 after restore:
        FAIL exactly one registration (the survivor's) after the restore got= want=1
        FAIL WE-AR reservation in force after the restore got=0 want=1

  `prstate` was empty and both assertions compared against the empty string. Those two lines concern the persistent reservation that all MXFS fencing rests on, produced by an unset variable on a run whose gate had certified, restored and published `P163-RECOVERY-COMPLETE` cleanly with 327/327 files verified, zero bad or missing. At face value they said "the reservation is gone after the restore": a critical fencing regression the run never observed. Lesson: `ck "<claim>" "$(measurement)" "expected"` cannot distinguish "the thing is broken" from "I could not look at the thing". When the measurement can come back empty, assert on emptiness FIRST and report it as a failed measurement that names itself a harness fault; otherwise every such gap enters the record as a defect in whatever the assertion was about. Fixed in 0.75.89, both halves: (1) `: "${MXFS_DEV:=<QNAP by-path>}"` at the top, the same default every sibling harness carries; (2) the PR-state block refuses to compare an empty reading and prints "the two reservation assertions below were NOT measured (this is a harness fault, not a fencing fault; do not diagnose the reservation from it)". Check elsewhere: any `set -u` harness whose env vars are only read inside optional arms has the same shape and will pass for months, then die inside the one arm that matters on the day it first runs. `trap-set-u-unbound-var-inside-a-conditional-arm-turns-into-two-false-fencing-FAILs`
- Never `grep -r` over `tests/`: `tests/evidence/` holds hundreds of run dirs with 13 MB journals each; the grep exceeded the 120 s Bash timeout and, run during a live rig lap, competes for the same disk that hosts the LUN, guest images and journal, which can invalidate the lap. Scope to source: `grep -rn PATTERN tests/suite tests/lib tests/*.sh` or `--include='*.sh'`. Same class as the ban on root-wide searches. `trap-never-grep-r-over-tests-evidence-journals-are-13mb-each-and-starve-a-running-rig-lap`
- Rebooted or destroyed nodes lose their kernel log: node journald is volatile (`/run/log/journal`; `/var/log/journal` files date from Jul 1), so `journalctl -k -b -1` after a `virsh destroy` returns 0 lines. Harnesses that power-cycle a node (lone_crash_replay, node_death_replay, tck) must capture `dmesg`/journalctl on the victim into `tests/evidence` BEFORE the destroy, or derive victim facts from the survivor's journal. The dmesg ring also wraps within minutes under a board. `trap-node-journald-volatile-rebooted-node-kernel-log-gone`

## 4. Harness setup traps that masquerade as product refusals

- Reusing a node id in a harness is a retired identity: `node_id_override` with an id that already departed in the peer's mount lifetime gets `P164-DEAD-NOTE` / `P164-DEAD-REJECT announce ... retired identity ignored`, active_count stays 1, the mount parks page requests and the harness's 40 s bound kills it. Not a filesystem defect (real ids are random 32-bit per incarnation). Pick a fresh id per rejoin or cycle the peer's mount between reuses (`tests/rejoin_residue.sh` arm 4 now uses ID_LOW+1 / ID_HIGH-1). `trap-reused-node-id-override-is-a-retired-identity-p164-dead-reject-peer-never-admitted`
- Bumping `MXFS_PROTO_GEN` (or any on-disk header the tools compile in) needs `make tools`; `make modules` does not rebuild `tools/`, so `mkfs_mxfs` stamps the old `cluster_proto_gen` and the first prep mount fails EPROTO ("Protocol not supported", dmesg `C7 gate: ... refusing mount`). EPROTO on the first mount after mkfs is this, not a transport-census refusal. `trap-proto-gen-bump-needs-make-tools-or-every-mount-is-refused-eproto`

## 5. Tooling side effects follow the tool, not the bytes

- The awareness `track` hook is PostToolUse on `Edit|Write|MultiEdit` only; `sync` (Stop) computes drift from that session ledger, not mtimes. Appending to `.claude/awareness/subsystems/*.md` with `cat >>` or a heredoc writes correct bytes but leaves the drift unresolved forever. Use Edit/Write on awareness docs. Generally which tool performed a file operation is semantic: `sed -i`, `cat >>` and heredocs are invisible to PostToolUse hooks, as are the ccmemory injection (on `Read`) and ledger guard. `trap-awareness-track-hook-only-sees-edit-write-not-bash-heredoc`

## 6. Build mechanics: green or zero without having built or tested anything

Source: `compiled-build-tauth-tests-and-harness-measurement-traps`. A sixth note from the same source, a probe missing from the built module, sits in section 2.

- **Bare `make -C tests/tauth` tests nothing.** The first rule in the Makefile is `obj/unowned_page_test.o`, so it builds one object and exits 0 in ~4 ms. These binaries are the only user-mode build of dlm.c and the ledger, so a green bare make proves neither compile nor test. Always `make -C tests/tauth test` (~1m38s on clyde after a dlm.c change; each test prints `=== <name> RESULT PASS fails=0 ===`). `trap-make-c-tests-tauth-without-a-target-builds-one-object-and-runs-no-test`
- **tauth test objects do not depend on `tauth_store.h`.** `struct mxfs_tauth_ledger` embeds `struct mxfs_tauth_store`, but the Makefile rules list only `tauth_ledger.h` and `dlm.h`. After a store struct change (0.90.85) stale objects read fields at old offsets: deterministic, plausible failures (`commits=0`, `gen_refusals +0`, a 300 s timeout in dlm_ledger_test). An A/B that toggled only the .c change failed both ways, which is what pointed at the build. After ANY change to `dlm/tauth_store.h`, `dlm/tauth_ledger.h`, `dlm/dlm.h` or `include/mxfs/mxfs_tauth.h`, run `make -B all` (or `clean`) in tests/tauth before reading a result. Do not edit the Makefile unasked; force the rebuild. `trap-tauth-test-objects-do-not-depend-on-tauth-store-h-so-a-store-struct-change-leaves-them-stale`
- **Top-level `make dlm/foo.o` builds USER-MODE objects into `dlm/`.** They have no `.o.cmd`, and the next `make modules` links them: `modpost: "READ_ONCE" undefined`. The failure prints `ERROR:` not `error:`, so `grep -c 'error:'` reads 0 while BUILD_RC=2. Per-object check is `make -C /lib/modules/$(uname -r)/build M=/src/mxfs dlm/foo.o`. Recovery: delete the affected `dlm/*.o` and `dlm/.*.o.cmd` by full name, no glob; chain launchers should grep `ERROR:`. `trap-toplevel-make-dlm-o-builds-usermode-objects-breaks-make-modules`
- **`make clean` also cleans `tools/`.** `mkfs_mxfs`, `chk_mxfs`, `resize_mxfs`, `fua_verify` vanish and the next prep fails `FS_PREP_FAIL: mkfs tool not found` after the fleet was already rmmod-ed. Any `make clean && make modules` chain ends with `make tools` (~2 s) before deploy. `trap-make-clean-removes-userspace-tools-run-make-tools`
- **Warning sweep without relinking.** `KCFLAGS=-Wextra` rebuilds all objects and relinks `mxfs.ko`, splitting a live rig sweep across two srcversions. `tools/warn_sweep.sh` replays each object's own `.cmd` command with three edits only: truncate at the first `;` (objtool exits 129 on /dev/null), drop `-Wp,-MMD,<path>`, rewrite `-o` to `/dev/null`; run from `/lib/modules/$(uname -r)/build`. 131 objects in ~85 s at -j6, nothing in the tree moves. Highest-yield class is `defined but not used`; a name with initialisers can still be unused (all four `.sync_lazytime` lines sat in a false `#if LINUX_VERSION_CODE` arm), so grep counting references does not answer it. The fix is verified by the warning disappearing. The remaining 20 `-Wtype-limits` sites are benign (`uint8_t namelen` vs `MAXNAMELEN`); do not re-derive. `technique-replay-each-objects-own-recorded-compile-command-to-ask-the-compiler-what-it-deleted-without-relinking`

## 7. Source location

Source: `compiled-build-tauth-tests-and-harness-measurement-traps`.

- **No source in a /tmp scratch copy of the tree**, even to avoid racing an in-flight rig chain's build; the user directive was emphatic after new files were written only in a scratchpad copy (`w038`). Edit in /src/mxfs; handle the race by sequencing: do not run `make` in the tree during a chain's build/proof stage; editing sources during prep/test stages is safe because the chain insmods the already-built .ko. `feedback-never-write-source-in-tmp-scratch-copy-even-during-rig-runs`

## 8. Harness and oracle assumptions that turn a harness defect into an apparent MXFS result

Source: `compiled-build-tauth-tests-and-harness-measurement-traps`.

- **A suite row graded on one transport is not coverage on another.** The first full `2 cawd` run failed three rows that had never run on CAW: `crash_audit` (TCP-only gate and authority-ledger asserts), a bare `grep 'P-RMAN-LOAD'` matching `P-RMAN-LOADED` (anchor on `P-RMAN-LOAD victim_slot=`), and `alloc_witness` modelling a node's AG as `slot % agcount` instead of `agno mod stride == slot mod stride`. Before claiming a suite passes on a configuration, check each row has a verdict ON it (`tools/criteria.py <N> <dlm>`); read the oracle before suspecting the kernel. `trap-a-suite-row-whose-oracle-was-built-for-one-transport-makes-the-other-transports-board-unpassable`
- **A knob a harness selects by must expose a counter reset on write.** Third occurrence of counting a budgeted probe's printed lines (first 8, then every 64th, per module load). Fix (0.84.2): readable module-parameter counters (`dl_drop_lockreq_n`, `dl_drop_grant_n`) and `module_param_cb` set-callbacks that reset counter and print budget on every arm or disarm. Reset must be in the write path, never lazy at next send, or a candidate that triggers no send inherits a stale count. The harness reads the counter and refuses a build without it. `dlm/dlm_user_compat.h` stubs `module_param_named`/`module_param_cb`/`struct kernel_param_ops`/`param_set_ullong` under `#ifndef __KERNEL__` because dlm.c is also built for tests/tauth. `technique-a-test-knob-a-harness-selects-by-must-expose-a-counter-that-resets-on-write`
- **A lone mount takes no grants, so writes no ledger pages.** The TCP authority ledger records grants, which come only from cluster acquires with at least two members. A takeover harness that had B unmount first and then created 32000 entries on A saw `cand=4`, a 2.3 s pass, and aborted every lap; earlier laps had worked only because a ~15k-page ghost from an older campaign sat in the ledger. Take the grants under two members, have the peer leave cleanly (handoff), X leaves last, and check `cand=` on the first lap of a fresh filesystem. `trap-a-lone-mount-takes-no-grants-so-it-writes-no-ledger-pages-for-a-takeover-harness`
- **A protocol wired to one transport looks like a decision on the other.** `v5_bootstrap_run` has one call site (`dlm/v5_mount.c`, CAW branch of `mxfs_v5_dlm_init`); TCP calls only `v5_bootstrap_setup`, which logs `P-BOOT-STATE IDLE` where the verdict would sit, so a concurrent whole-cluster restart (0.89.38) left both mounts refused with unreplayed journals. Before concluding a protocol "decided not to act", find its call sites and the branch they are in. Make decision functions incapable of returning silently (`P-BOOT-SKIPPED`, `P-BOOT-SCAN-VERDICT`) so a missing line is evidence. Porting to TCP must not let an adopted slot alias a dead node's PR holder bit: EXCLUSIVE authority is keyed by `auth_node`+`auth_inc`, SHARED is slot-indexed. `trap-a-recovery-protocol-can-be-wired-to-one-transport-only-and-the-other-transports-silence-looks-like-a-decision`

## 9. Guards in shared helpers

Source: `compiled-build-tauth-tests-and-harness-measurement-traps`.

- **A recompute-and-compare guard must use the caller's mapping** (0.75.18 to 0.75.19). A check added inside `dlm_page_hand_to` compared against `dlm_page_owner` (active_nodes[page % N]), but `mxfs_dlm_handoff_depart` targets others[page % (N-1)], the view without the departing node. Every clean-leave hand-off was refused (`P-TAUTH-HANDOFF-STALE-TARGET why=depart`), the successor's mount parked on the root page, and 17 of 24 armed rejoins took 14 s instead of 1 s. The guard's probe on the node being watched read zero because the refusals were on the departing node. Rules: list every caller and confirm they compute the compared value the same way, or pass the expectation in; a guard that can refuse needs a probe on every node it can fire on, and the first lap must grep all journals; fixed with `bool departing` (a departing node requires only a live member target). `trap-a-re-validation-guard-must-use-the-callers-mapping-depart-handoff-maps-the-view-without-self`

## Standing checks

Before trusting a null: what writes this number and when; can the probe's full guard chain be satisfied on my path; can the measurement come back empty and be mistaken for a result; did my own filter or search remove or starve the evidence; did the build target I ran compile and test what I think it did, against current objects (section 6).
