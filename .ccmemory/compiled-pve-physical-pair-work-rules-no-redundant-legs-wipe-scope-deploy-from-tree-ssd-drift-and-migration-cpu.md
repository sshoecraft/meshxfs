## Hardware: never reset the physical pair

From `compiled-pve-physical-pair-test-rig-traps`.

- The user first said "pve1 is old hw like pve2 dont break them" after a failover suite sysrq-reset pve1 three times in ten minutes. pve1 then stayed down about 37 min and came back about two minutes after Wake-on-LAN packets were sent (likely the wake, not proven). `feedback-the-physical-pve-pair-is-old-hardware-so-minimize-hard-resets-and-restore-without-one`
- This escalated to a hard prohibition. Resets "fried" the old pve2 and it no longer boots. Never reset, reboot, crash, sysrq or power-cycle pve1/pve2. That covers every crash/reset/power step of `tests/pve_pair_failover.sh` and `tools/pve_power.sh off|on`. Crash, reset and outage testing runs on the nested pair only. A defect record whose next step says "verify on the physical pair" with a crash step is verified on the nested pair, and the record says so. `feedback-never-reset-reboot-or-power-cycle-the-physical-pve-pair`
- The one narrower approval on record (user, 2026-10-14) is under "User AFK" below: hard resets of the physical pair for the final release-validation run only, and still never pve1.
- Non-destructive work on the physical pair is still fine: installs that stop and start units, loads, tree walks, profiles. Announce anything that interrupts service first.
- If a host is left in a bad state, restore without a reset: `tools/pve_power.sh restore <addr>` lifts the isolation and starts mxfs-drbd-guard then mxfs-drbd@mxfs (pve2 was back Connected Primary/Primary UpToDate in 95 s). If a host does not answer, send `tools/wake_on_lan.py <mac> 192.168.1.255` before declaring it dead. A reset is the user's call.
- Host power: clyde and both pve hosts share unprotected power (no UPS). When pve1 and pve2 both show a previous boot with no shutdown sequence within seconds of each other, run `journalctl --list-boots | tail -3` and `uptime` on clyde before blaming MXFS. A clyde restart in the same minute means power. A clyde restart also kills the netconsole listeners (restart them with `tools/pve_netconsole.sh start`), the nested pair VMs (not autostarted) and any lap driver waiting on them. pve1 does not reliably power on after AC loss, so use Wake-on-LAN. An unplanned outage is a free power-cut test: check the pair rejoined and run `chk_mxfs` while unmounted. `trap-clyde-and-both-pve-hosts-share-unprotected-power-so-a-joint-crash-is-checked-against-clydes-boot-list-first`

## User corrections on running work on the pair (2026-10-09 release work, 0.90.111-0.90.115)

- **Do not queue a validation leg an earlier run already covered.** After 10+ VM build legs on the physical pair in one day, a further 50-minute leg was queued for the final build, although the fix was a runtime knob and two knob=1 legs had already exercised the identical code path (the final build differed only in the knob default and a log string). Before queuing any run, list what earlier runs (this session and prior transcripts) already exercised on the same path; run only what tests something new: the crash/takeover suite on the nested pair plus the gates scripts/release.sh actually enforces (README text check, tests/full_verify.sh STEPS=build,packages,platforms, tests/drbd_release_verify.sh, release-matrix boards). "Look at the transcripts" about testing means the assistant's own prior test runs, not the user's typed messages; launching an agent to extract user messages was the wrong reading. `feedback-do-not-rerun-a-physical-pair-build-leg-the-ab-already-covered`
- **A destructive disk request naming one host never extends to the other.** The user asked to wipe pve1's sdb (old OS install, inspected only there). The session wiped both hosts' sdb (wipefs -a + sgdisk --zap-all), destroying pve2's Intel RAID (isw) signature and partition table before the user had looked at it. Pair symmetry made "do both" feel implied; it was not. Wipe, format, mkfs, create-md, pvcreate and the like apply only to the named host's disk. For the symmetric host, report read-only (lsblk, wipefs -n, pvs) and ask first, even if the plan needs both. `feedback-a-wipe-request-naming-one-hosts-disk-never-extends-to-the-other-host`

## Deploying and launching

Bullets dated 2026-10-09 come from the 0.90.111-0.90.115 work; the others from `compiled-pve-physical-pair-test-rig-traps`.

- **Test builds go to pve1/pve2 straight from the working tree**, not by commit, push and pull on the nodes: the user called that "unnecessary churn". Run git only when the user says so. The clone/pull/`make install` path is tested when the user asks for a release. `feedback-test-builds-go-to-the-physical-pve-pair-directly-never-by-commit-push-and-pull`
- That note's recipe: rebuild the module on each host (`scripts/pve_dkms_rebuild.sh`, described there as reading clyde's NFS /src), then swap it in with `scripts/pve_pair_update.sh SKIP_INSTALL=1` (`CHECK=1` adds a cold `chk_mxfs`); confirm the loaded srcversion equals the tree's (`modinfo -n mxfs`) before measuring. The next bullet breaks the first step on hosts without /src.
- **Trap (2026-10-09): PVE hosts do not mount clyde's /src, so `scripts/pve_dkms_rebuild.sh` exits 127** (no /src/mxfs on the physical pair 192.168.1.80/.81 or nested pair B 192.168.120.211/.212). The following `SKIP_INSTALL=1` update then silently reloads the OLD installed build (0.90.114) and reports success. Deploy a working-tree build with `FROM_TREE=1 scripts/pve_pair_update.sh` (~8 min on the physical pair; `CHECK=1` for a cold chk_mxfs), and always read back `/sys/module/mxfs/version` on both hosts. Host-built srcversion differs from clyde's (different kernel): compare the version string and the log's `installed=` srcversion. `trap-pve-hosts-do-not-mount-clyde-src-so-dkms-rebuild-fails-use-pair-update-from-tree`
- **The pve_* harnesses disagree on their default pair.** `tests/pve_cluster_write_authority.sh` defaults PVE_PAIR to nested pair A (192.168.120.137 / .192). `tests/pve_churn_fairness.sh`, `tests/pve_pair_profile.sh` and `scripts/pve_pair_update.sh` default to the physical pair. A "physical-pair verification" churn launched without PVE_PAIR ran on the nested pair, overlapped a fairness profile there, and the physical counters read 0. Always pass `PVE_PAIR="<addr> <addr>"`, check that the evidence's host lines name the intended pair, and never run two workloads on one pair at once. `trap-pve-test-scripts-default-to-different-pairs-so-always-pass-pve-pair`
- **In bash, `a > f; echo rc >> f & b ...; wait` backgrounds only the `echo`**, so job A ran in the foreground and job B started after it (about 8 min each, serially, and B's log did not exist while A ran). Group each job: `( job1 > l1 2>&1; echo "RC=$?" >> l1 ) & ( job2 > l2 2>&1; echo "RC=$?" >> l2 ) & wait`. Check that each log exists right after a parallel launch. `trap-ampersand-after-a-semicolon-list-backgrounds-only-the-last-command-so-two-jobs-run-serially`

## Live-migration test guests (2026-10-09 work)

- **A live migration test guest needs a common CPU model and ssh, not guest-exec.** pve1 is a Xeon W3520 (Nehalem, no AES-NI/AVX), pve2 a Core i3-8100. A `cpu: host` guest completes RAM copy then the target QEMU dies ("Failed to set special registers: Invalid argument"); that is CPU mismatch, not storage/MXFS. Use `qm set <id> --cpu x86-64-v2` (default x86-64-v2-AES will not start on pve1); packer build VMs (alma9-X1/X2) are cpu: host so clones need the override. Build guests' qemu-ga refuses guest-exec; drive them over ssh as root with tools/mxfs_sshpass.sh. A writer told to stop never acknowledges a pause: the harness final check must wait for the writer's own exit marker. With these fixed, 6/6 migrations PASS data-wise, downtime 0.4-2.5 s. `trap-pve-live-migration-test-guest-needs-a-common-cpu-model-and-ssh-not-guest-exec`

## Reading results correctly

- **Spare SSDs (Kingston SVP100S, 2011-era SATA, no native FUA) stall ~1 s on flushes for minutes after heavy writes (2026-10-09 work)**, so back-to-back storage comparisons measure run order. Evidence: LVM-on-DRBD run first 7/7 builds in 1410-1635 s vs MXFS run after it 3/7 in 2730 s; vmio matrix's last run read 2-5x slower; the same MXFS test on a fresh fs read 26.9 MiB/s; a run 40 s after packer deleted VM images read 5x worse. Proof on the raw DRBD device with no filesystem (tests/pve_small_write_stall.sh, tests/pve_bio_census.py): stall fraction 69/58/47/37% across four identical passes, falling with time. The hypothesis that MXFS's 512 B register writes caused the stalls was DISPROVED by that run. Use scripts/pve_build_compare.sh (blkdiscard sdb on both hosts per leg, idle SETTLE_S, alternate legs mxfs lvm mxfs lvm so drift shows as same-storage legs disagreeing); compare p50/p90 and stall fraction, never the mean; keep the pair idle before measuring. `trap-pve-spare-ssds-slow-for-minutes-after-heavy-writes-so-back-to-back-storage-comparisons-are-confounded`

From `compiled-pve-physical-pair-test-rig-traps`:

- **Clock skew after a reset.** A reset Z400 starts from the RTC and chrony only slews. pve1 ran 237 s fast, so wall-clock journal times misplaced a boot (network-online at 224 s vs 15.5 s monotonic), and a defect record was drafted on the wrong numbers. `tests/pve_pair_failover.sh` uses `journalctl --since @$t0` with t0 from clyde's clock, so the window reached into the previous step and answering-restart reported "recovered 2 s after its reset". Use `journalctl -b -o short-monotonic` (and `-k`) for boot timing. Compare `date +%s` on the host with clyde's before trusting a log-window verdict. Take t0 from the host being read. Fix the source with `chronyc makestep` then `hwclock --systohc`. `trap-a-reset-pve-hosts-journal-runs-minutes-off-until-chrony-slews-so-time-a-boot-in-monotonic-seconds`
- **Rig kernel-log volume is not production.** `tests/setup/prep_node.sh` loads mxfs with `dyndbg=+p` (1591 of 1593 sites on), so a rig node logged about 165k lines in 4 min of I/O (iomap addr, buf_io, P71/P239-P241). Never cite that as production log volume or compare rig latency/IOPS with a production node without saying so. Count flags with awk on field 3 of `/proc/dynamic_debug/control`, not `grep '=p'`. On the rig, a missing probe line is real absence. `trap-rig-nodes-print-every-mxfs-debug-site-so-their-log-volume-and-latency-are-not-production`
- **Anything written to the kernel log with an `mxfs` prefix reads as MXFS spam to the user** (it would annoy a lot of people). pve1's steady 243 lines/h were `mxfs-diag-heat` from `tools/pve_crashdiag.sh on`, while the module logged 4 lines. Split by source before judging a rate: `journalctl -k --since -60min -o cat | grep mxfs | sed -E 's/[0-9]+/N/g' | sort | uniq -c`. Install kmsg-writing diagnostics only on the host under investigation and turn them off afterwards (`tools/pve_crashdiag.sh off <host>`). `feedback-a-diagnostic-that-writes-mxfs-prefixed-lines-to-the-kernel-log-reads-as-mxfs-spam-to-the-user`
- **A time-limited fio writer leaves its laid-out tail unwritten.** fio `--time_based --runtime=N` on a `--size` file lays the whole file out, writes only as far as N seconds reach, and a later `--verify_only` reads the unwritten tail as zeros ("got pattern '00'"). Before calling it corruption, compare the first bad offset with the job's `write.io_bytes`. They matched exactly on the nested pair. For a write load checked afterwards, make writers size-based (`--loops` for duration) or verify only `io_bytes`. `tests/pve_pair_write_bound.sh` does the former, with `verify_pattern=%o`. `trap-a-time-limited-fio-writer-leaves-its-laid-out-tail-unwritten-and-verify-reads-zeros-there`
- **osimager proxmox builds that log `Using SSH communicator to connect: <no value>` never connect** and die at packer's 45 min `ssh_timeout`, on any storage. The cause was `ssh_host` rendered as `{{ .Host }}` for platform proxmox, and the owner fixed it. Do not read such a build's rc as a verdict on storage. Check the step it died in, and judge storage by install time (`qm agent <id> get-host-name`, or `scripts/pve_pair_builds.sh` "installed after N s", `STOP_INSTALLED=1`). The 45 min bar is real for the owner's workflow. `trap-osimager-proxmox-builds-never-connect-over-ssh-so-every-build-times-out-on-any-storage`

## Kernel trap found on the PVE 6.17 kernel

From `compiled-pve-physical-pair-test-rig-traps`. From Linux 6.17, iomap leaves the ended ioend in `wpc->wb_ctx` when `->writeback_submit` returns an error. An fsync pass resubmits it for every later folio and once more at the end, giving a double `bio_endio` and `BUG at mm/slub.c:563` in `iomap_finish_folio_write` (measured on the nested pair with `tests/pve_wb_refusal.sh`). The physical pair saw one ioend refused 11 times and an fsync hung on a folio lock. Any 6.17+ `->writeback_submit` must clear `wb_ctx` after handing off the ioend (`mxfs_ioend_hand_off` in `pal/linux/xfs_aops.c`), and every new error return in that hook goes through it. Before 6.17 the `->prepare_ioend` path was safe. `trap-iomap-6-17-keeps-an-ended-ioend-in-wb-ctx-after-a-failed-writeback-submit`

### Trap: inode reclaim vs drop_caches in the bmbt join-window test

`trap-drop-caches-cannot-reclaim-an-inode-without-its-buffers-and-xfs-reclaim-walk-cursor`
Four traps that made `tests/bmbt_join_window_repro.sh` read VACUOUS/CLEAN for months (D-BMBT-TENURE-END, closed 0.90.129), plus a control-design note:
- A node-side script launched from `$PWD` on clyde is `/home/steve/src/mxfs/...`; nodes mount the tree only at `/src/mxfs`. The loop never ran and every arm graded on silence. Launch node-side scripts from `/src/mxfs/$OUT/...`.
- `echo 2|3 > drop_caches` cannot produce "inode reclaimed, its cached metadata buffers still there". drop_slab runs the xfs buftarg shrinker in the same pass and loops until little is freed, so the bmbt buffers die first/with the inode (measured: buffers gone, inode and its DLM grant kept). To end one inode's tenure without the buffer shrinker use an in-kernel injector: xfs_iget(INCORE) -> d_mark_dontcache -> d_prune_aliases -> xfs_irele -> xfs_reclaim_inodes_nr (see `dbg_join_window_reclaim_ino` in `xfs/xfs_mxfs_join.c`).
- `xfs_iget(..., XFS_IGET_INCORE)` failing does not mean the inode left the cache: it also refuses a cached IRECLAIMABLE / inactivating inode, which still holds its grant. Read pag_ici_root directly (radix_tree_lookup under RCU) and report i_flags.
- One `xfs_reclaim_inodes_nr` call can miss an inode: the RECLAIM walk starts at pag_ici_reclaim_cursor and stops at the AG end (resetting the cursor to 0). Call it twice.
- General: a mode-2 "positive control" that loops drop+read every round also races the census; a single-shot control (once, then idle) is what proved the census could see blocks at all.
