This is an `assorted` merge: the articles share no single topic. Part one is a rig-side rule (session-side recursive reads of the evidence tree contaminating running laps). Part two is a set of code-level and harness/measurement traps (kernel API, on-disk checks, guards, allocator liveness, mount ordering, where a run reads, what it counts, how it is launched). Part three (absorbed from `compiled-run-sh-rig-lock-and-harness-traps-plus-transport-parity-gaps`) covers the `/tmp/mxfs_run.lock` rig lock, run.sh / drbd_rig.sh scripting traps, the `1/xfs` boot-disk default, and four code-level traps where state or behaviour is silently absent on one path (cluster boundary loose; grouped by what each note teaches).

# Part one: recursive reads of the evidence tree

## Trap
`never-grep-r-tests-evidence-while-lanes-run-it-shares-the-lun-pool-ssd`: `tests/evidence` is a symlink to `/src/mxfs-evidence`, on `/dev/sda`, the one SATA SSD that also holds every SCST pool LUN image (`/mxfs`, `/home/steve/disks/pool`). A recursive read of the evidence tree (`grep -rl <batch id> tests/evidence`) reads ~500 MB/s and drives sda to 100 % util for minutes.

## Observed 2026-10-24 (0.90.134 attempt 19)
- A session's `grep -rl 'b20261024-d04ebf' tests/evidence` ran 16:10:37Z-16:13:56Z (backgrounded at its 120 s tool timeout).
- clyde sysstat (`sadf -t -d /var/log/sysstat/sa24 -- -d -p`, CDT): sda rkB/s 238461 at 11:11:01; 539491 / 510022 / 473715 at 11:12-11:14 with %util 100.00 / 99.99 / 92.84; then 6702 at 11:15.
- In those minutes two laps failed: verification b20261024-0fd280 lap 12 (workers 3 of 20 rounds, remount hung 68 s, killed at 130 s; it ended an 89-lap verification) and control b20261024-aefae7 lap 10 (prep over 88 s, log-slice zero_ms 13679/16208 vs 1030-6902).

## Cost beyond the lost laps
The release-reviewer REJECTED the infra-proven claim for lap 12 (P20261024-a96a97): coincidence in time is not a measured link, the lap kept no node kernel log, and an earlier lap passed in a 61 % minute. A session's own I/O can therefore leave an unexplained failure that must be recorded as a defect and reproduced under control. A failed lap the session caused cannot simply be written off.

## How to apply
- Never `grep -r`, `du`, `find` or any recursive read over `tests/evidence` while any rig lane runs. Locate a batch's laps through the ledger (`grep -n <batch> data/criteria.runs.jsonl`): lap logs are `tests/evidence/batch_laps/<batch>/*.log`, lap evidence directories are `tests/evidence/<stamp>_<tag>_<label>`, or `ls -d` a known stamp prefix.
- When a lap is slow or overruns, check sda (`sadf -t -d /var/log/sysstat/saDD -s HH:MM:00 -e HH:MM:00 -- -d -p | awk -F';' '$4=="sda"'`, 1-minute samples in CDT) and the session's own commands at that time. An infra claim still needs the nodes' kernel logs for the window.
- Related: [[compiled-scst-shared-target-caw-latency-lap-bounds]].

# Part two: code-level and harness traps
(Absorbed from `compiled-code-and-harness-traps-vfs-helper-recursion-identity-crc-guard-symmetry-and-loop-stdin`; the `trap-...` names below are the raw notes it had folded.)

## Code-level traps

**Same name, different function across kernel versions.** `trap-a-vfs-helper-that-keeps-its-name-across-kernel-versions-can-become-the-dispatcher-that-calls-you-back`: `inode_update_time(inode, flags)` on 6.x is the dispatcher into `->update_time`. On 7.x the same name is the helper that sets stamps and returns I_DIRTY_*. Called from inside `xfs_vn_update_time` on 6.x, it calls itself: 169 alternations, stack guard page, panic. The compiler cannot warn, because the older signature accepts the call. Before calling a same-named function under an `#else` arm, read its body in the older tree. Fix: take upstream 6.8's branch verbatim (`generic_update_time`) and use the guard `flags != (I_DIRTY_SYNC | I_DIRTY_TIME)`. The pre-5.12 guard `!(i_state & I_DIRTY_TIME)` is false on every call since 5.12, so the hook was inert. A live lap found the panic first, not the durability question it was built to ask.

**A CRC over a mutable field.** `trap-a-crc-that-covers-a-mutable-flag-field-invalidates-an-intact-identity-block-and-the-fix-reached-only-one-of-its-readers`: the disklock identity CRC covers `hb->flags`, but the guard writers move a victim to RECOVERY_GUARD without re-binding it, so an intact block reads invalid. The first fix (`mxfs_hb_guard_identity_valid`) reached only the admission reader. `dlm/bootstrap.c` kept the strict predicate and counted the guarded victim `noident`; `P-BOOT-KEY-UNCLASSIFIED` then refused bootstrap and no node could mount (`MOUNT_RC=32`). Lessons: prefer not covering a mutable field; when a laxer predicate is added beside a strict one, enumerate the strict one's callers then (`grep -n mxfs_hb_identity_valid dlm/*.c`, check each for a flags test excluding RECOVERY_GUARD).

**A guard written for the self direction.** `trap-a-guard-written-for-the-self-direction-leaves-the-symmetric-peer-direction-open`: the SCSI PR key is per boot, so two incarnations on one host share it. `P238-FENCE-OWN-KEY` blocks preempting our own previous incarnation, but a peer fencing a dead incarnation whose host has remounted preempts the live successor. When a guard's predicate names self, substitute any other live member and ask if it is reachable. Enforce at the primitive callers funnel through (`mxfs_scsipr_fence_node`, which covers all four fence paths). Exclude the victim by node id, not liveness alone. The guard fails closed, so test both directions: a control arm with a key nobody holds must not trigger it.

**Userspace SCSI tool and FUA.** `trap-a-userspace-scsi-tool-that-sets-fua-in-the-cdb-fails-every-command-on-the-shipping-lun`: the 2/tcp LUN answers READ(16) with FUA or DPO with ILLEGAL REQUEST 24/00. The kernel (`pal/linux/kern.c`) latches `mxfs_fua_read_unsupported`; `tools/recov_forge`, `caw_slotdump` and any new CDB-building tool do not. Mirror the fallback (retry once without FUA, latch, say so on stderr). A non-FUA read is fine for a sector you wrote yourself through the same nexus, not for arguing another initiator's write reached the platter. Never remove FUA unconditionally. `recov_forge` is built by no Makefile; a stale checked-in binary silently runs old code, so a harness must `cc` it first.

**Geometry macros before `xfs_mountfs`.** `trap-a-mount-hook-before-xfs-mountfs-cannot-use-the-fsb-to-daddr-macros-because-m-blkbb-log-is-still-zero`: `m_blkbb_log` is set only inside `xfs_mountfs`. Earlier in `xfs_fs_fill_super`, `XFS_FSB_TO_DADDR` and friends return fs blocks, off by 8x. The slice lifecycle zeroed 64 MiB of the data area at the wrong offset while the harness said READY and the control passed. In pre-mountfs code derive from `mp->m_sb` directly (`sb_agblklog`, `sb_agblocks`, `sb_blocklog`). Print the absolute offset acted on and compare it to an independent tool (`tools/slice_image.py geom`). A harness asserting only the fix's own log line passes a fix that hit the wrong bytes; the platter-side assertion carries the verdict.

**AG-exhausted vote.** `trap-withholding-the-ag-exhausted-vote-from-own-refusals-hangs-a-create-whose-sole-free-number-is-refused-for-good`: D-DIALLOC-REPICK-STORM carved 24 inode chunks against a one-chunk reservation. Making `swept` vote only on peer contention hung the create where the sole free inode number was refused for good (ILOCK held, 120 s budget abort, test1 power-cycled twice). `swept` means "no usable candidate this lap", whoever refused. Bound the dangerous action at the action (one carve per `xfs_dialloc` call, `mxfs_dialloc_carve_gate`, `P-DIALLOC-CARVE-BOUND`) and leave the signal honest. Reset `rs->swept` per AG. When a flag feeds two consumers, starving it to fix one starves the other. Verify a storm fix with the non-storm phases too.

## Harness and measurement traps

**Detectors run on nodes.** `trap-suite-detectors-run-on-the-nodes-where-no-ssh-credentials-exist`: `tests/suite/*.sh` detectors execute on the test nodes, which hold no ssh secrets. A helper reaching another host fails silently and returns its "unknown" path, so the cell shows SKIP with the wrong reason (`tools/mxfs_rig_tag.sh` read the LUN vendor over ssh). Read the node's local sysfs first; use the `/src` NFS mount for repo facts; for cross-node facts record them in the cluster marker at prep time. Verify the helper from the node: `tools/mxfs_sshpass.sh test1 "cd /src/mxfs && ./tools/<helper>"`.

**Busy text is not a cause.** `trap-mount-busy-covers-two-different-ebusy-causes-and-the-discriminator-is-whether-the-kernel-began-a-mount`: `mount(8)` prints "mount point busy" for every `-EBUSY`. A 2 s leftover holder is vacuous; a 123 s admission-barrier refusal is the measurement. A vacuity gate that exited before taking the kernel window discarded the only evidence. Take the window first, then classify by whether the kernel saw a mount (`P304-PREOBSERVE`, `P-BARRIER-CLOCK`, `P240-QUAR-IMPORT`, `Mounting Filesystem`), not by message or wall time. Capture evidence before classifying. The exit path must restore everything the lap took, including remounting the fleet.

**Key spelling.** `trap-a-kernel-printed-hex-key-is-unpadded-and-compares-unequal-to-a-zero-padded-normalization`: kernel `%llx` is unpadded, `normkey` pads to 16 digits, so about one key in sixteen (top nibble zero) fails an identity assertion from two spellings of one number. Normalize both sides of every key comparison.

**Run-id ties.** `trap-two-board-rows-tied-by-the-run-id-must-run-in-one-run-sh-invocation-or-the-second-reads-indeterminate`: `alloc_witness` seals evidence under its run id and `chk_clean` refuses a witness from another run as INDETERMINATE (by design; an insufficient witness yields VACUOUS). Two `./run.sh` calls give two run ids. Rows sharing evidence go in one call: `./run.sh 2 tcp alloc_witness chk_clean`. Read the INDETERMINATE reason text before calling it a design outcome.

**Stdin in loops.** `trap-a-harness-run-inside-a-while-read-loop-drains-the-manifest-as-its-stdin-and-the-loop-runs-one-entry`: a harness run inside `while read ...; done < manifest` inherits the manifest as stdin, and an ssh that does not redirect stdin swallows the rest. The gate reported `PASS entries=1` for a 55-entry manifest. Put `< /dev/null` on every command in the loop and compare `entries=` to the manifest count. `trap-a-selection-step-keyed-on-a-cumulative-dmesg-count-picks-the-previous-runs-target` has the same bug in its candidate search; use `done 3< file` with `read ... <&3`. Also from the first note: an identity read (`chk_mxfs -v`) taken while another harness formats the LUN is a torn read, not a defect; resolve again and compare.

**Selection from a cumulative dmesg count.** `trap-a-selection-step-keyed-on-a-cumulative-dmesg-count-picks-the-previous-runs-target`: `tests/tcp_lockreq_blackhole.sh` chose its target inode from an unscoped `dmesg | grep -ac`. The ring survives module swaps, so run s578c inherited 15 hits from the previous run, armed the fault on an inode locally mastered in that incarnation, and printed nine PASSes, including its own vacuity gate, without touching the code under test. Mark the log at run start and scope every count to the mark. A vacuity gate compares to a baseline sampled immediately before the measurement, not to zero. Mastership is a hash over resource id and active node set, so it changes per cluster formation; rediscover the target each run and never cache an inode number across a module swap.

## Common thread (part two)

A check that passes is only as good as what it measured. Several traps share one shape: the signal read is not the property claimed (message vs cause, log line vs platter, cumulative vs scoped count, one reader of several, self vs peer direction), and the harness reports PASS regardless.

# Part three: run.sh / drbd_rig.sh rig-lock traps, harness coverage gaps, silent transport/ordering traps
(Absorbed from `compiled-run-sh-rig-lock-and-harness-traps-plus-transport-parity-gaps`, which itself had absorbed `compiled-run-sh-1-xfs-baseline-defaults-to-dev-sda-boot-disk-off-qemu-rig`, a one-note assorted group; raw note names below are the notes it folded.)

## A. The rig lock (`/tmp/mxfs_run.lock`) and who holds it

- **Never overlap run.sh with a live drbd_rig.sh**, even on a different rig group (and including a harness's `prep_cluster`). drbd_rig.sh takes the lock SHARED via `tests/lib/runlock.sh`, but run.sh's orphan check only recognises run.sh process trees, so it prints `WARN: ... held only by orphans of a dead run.sh — reaping` and kills drbd_rig's ssh/LUN-login children (drbd_rig exited 143 mid-LUN-allocation). Sequence them. `trap-run-sh-reaps-a-live-drbd-rig-sh-as-orphans-of-a-dead-run`
- **A daemon started inside run.sh inherits its lock fds.** The netconsole `socat` listener launched by `tools/netconsole_listen.sh start` via `nohup … &` inherited `exec 9>"$RUNLOCK"` and held the lock from PPID 1 after the run ended. The old exclusive path reaped it silently on every next whole-rig run (prep then restarted it); a shared rig-group lock just failed. Anything that must outlive a lock holder closes inherited fds above 2 first; rig-group runs use dynamic fds (`exec {fd}>>`), not just fd 9. Verify with `ls -l /proc/<pid>/fd` (never `cmdline`). `trap-a-daemon-started-inside-run-sh-inherits-the-rig-lock-fd-and-holds-it-after-the-run-ends`
- **`timeout N ./run.sh … | tail` does not stop the board.** `timeout` signals the pipeline's reader; the pipeline status is `tail`'s (exit 0), run.sh keeps running as an orphan and holds the lock, so later runs exit 3 ("another run.sh holds /tmp/mxfs_run.lock") with no evidence dir. A driver that then takes "the newest evidence dir" re-scores the previous lap (four A/B laps "reproduced" a failure none ran). Redirect to a file instead; a run is finished when `.last_run.json` and `tools/criteria.py` show no PENDING rows; use `fuser` + `/proc/<pid>/stat`,`comm` to see whether the holder is progressing before killing it (killing mid-flight leaks the module refcount and breaks next prep); drivers must require a NEW evidence directory. `trap-timeout-around-run-sh-piped-to-tail-kills-the-reader-not-the-run-and-orphans-the-cluster-lock`
- **A filtered run after a rebuild needs `prep_cluster` ALONE first.** The cluster marker `.cluster_marker.<group>.json` must name the same config and srcversion; the forced-prep branch requires `ONLY == (prep_cluster)` exactly (~run.sh:2103), so listing it with other tests does not help. Two invocations: prep, then the test. A node set mounted by `drbd_rig.sh mxfs` does not satisfy the marker. `technique-a-filtered-run-sh-after-a-rebuild-needs-prep-cluster-run-alone-first`

## B. Harness scripting and coverage

- **Bare `wait` in a script that keeps LUN-holder background processes never returns** (`tail --pid=$$ -f /dev/null &` per allocation lives until the script exits; drbd_rig.sh `up` sat in `wait` from 20 s to its 620 s budget). Collect `$!` per job and `wait "${pids[@]}"`; kill holders in an EXIT trap (tail notices pid death only on a ~1 s poll, so an immediate re-invocation saw "test1 is held by lun03's allocation"); spawn holders with lock fds closed or they keep the node/config flocks. Also never edit a bash script while an invocation is live: bash resumes at a byte offset and re-reads the new text. `trap-a-bare-wait-in-a-script-that-keeps-a-lun-holder-process-never-returns`
- **A rig that reformats before every mount never exercises remount or retirement.** On the DRBD attachment a clean unmount leaves the heartbeat slot RETIRE_PENDING with key 0 (settled only by SCSI PR evidence): remount hung in admission (P-ADMIT-RETIRE-PENDING-HELD), whole-cluster restart was refused (P304-RETIRE-UNKNOWN-STALLED). Two sessions passed because `drbd_rig.sh mxfs` and run.sh prep both mkfs first. For any new attachment/transport/retirement path test: one node unmount+remount with peer up (several cycles), and all-nodes clean unmount then mount without mkfs. Now covered by `scripts/drbd_rig.sh remount-test`. `trap-a-rig-that-reformats-before-every-mount-never-exercises-remount-or-retirement`
- **`run.sh 1/xfs` defaults `MXFS_DEV` to `/dev/sda`, which is the boot disk off the qemu rig** (source: `compiled-run-sh-1-xfs-baseline-defaults-to-dev-sda-boot-disk-off-qemu-rig`, a safety trap on any platform other than the qemu rig). `run.sh` takes the `1/xfs` native-XFS baseline's device from `data/configurations.json`, and that default is `/dev/sda`. It means "whatever LUN the live rig presents at sda", which is true only on the qemu rig. Multi-node configurations borrow a pool LUN instead, so they never hit this. On 2026-10-13, `MXFS_NODE_LIST=vstest1 ./run.sh 1/xfs prep_cluster` on a vSphere guest sent `sg_persist --clear` to the boot disk and ran `mkfs.xfs -f /dev/sda`. The kernel refused the exclusive open ("/dev/sda: Can't open blockdev") because sda's partitions were mounted; that is the only reason the root filesystem survived.
  - Guard: `tests/setup/refuse_inuse_dev.sh` now guards both preps: it refuses a device with partitions, holders, mounts, or swap/LVM/RAID signatures. Still:
  - Off the qemu rig, ALWAYS pass `MXFS_DEV` as the shared LUN's stable by-path link, e.g. `MXFS_DEV=/dev/disk/by-path/ip-192.168.120.1:3260-iscsi-iqn.2026-05.local.mxfs:pool-10-lun-0` on vstest1.
  - `1/xfs` also needs `MXFS_NODE_LIST` with exactly one node, and its own `prep_cluster` before `fio_perf`.
  - On vSphere the shared LUN is sdb; sda is the VMware boot disk.
  - Never trust a harness's default device on a platform it was not written for. Read `lsblk` on the node first. Provenance: ccloop run 8bd0eed0, session 3. `trap-1-xfs-baseline-default-dev-sda-is-the-boot-disk-off-the-qemu-rig`

## C. Code-level traps (state or behaviour silently missing on one path)

- **Post-mountfs initialiser zeroing state the mount barrier wrote.** `mxfs_dlm_cache_init` runs AFTER `xfs_mountfs` and `bitmap_zero`'d `m_mxfs_foreign_dead_slots`, discarding the barrier's handoff (`P-OBL-BARRIER-OPEN slot=1`). The reap worker saw an empty dead set, cleared the replay duty (`bitmap_subset` of two empty sets is true) and swept into a frozen AG: `P-OBLF-AG-WAIT`/`TIMEOUT` after 120 s, kworker in D state. Check call order in xfs_super.c before passing barrier state through mount fields (`mxfs_defer_reap_init` before, `mxfs_dlm_cache_init` after); a later `bitmap_zero` on a kzalloc'ed struct is a discard; a sweep blocked on a freeze is a symptom, find who emptied the set. Hidden because only a case first met inside the barrier hits it. `trap-a-post-mountfs-init-that-zeroes-state-the-mount-barrier-already-wrote-drops-the-barriers-handoff`
- **Hand-numbered inode flag bits shared bit 28.** `MXFS_IF_ACQ_REFUSED` and `MXFS_IF_ADOPTED_UNLINK` were both `1U<<28` in xfs_inode.h; a DLM denial read as freer authority at inactivation. Fix: `scripts/inode_flag_bits_audit.py` (step of `tests/full_verify.sh`), `static_assert(MXFS_IF_ALL_FLAGS == MXFS_IF_ALL_FLAGS_SUM)` in the header (sum equals OR iff no shared bit), a second assert against upstream XFS flags, and ACQ_REFUSED moved to `1UL<<32` (added to `XFS_IRECLAIM_RESET_FLAGS`; 64-bit pinned). `XFS_IPINNED` (bit 8) is a wait-bit key, so FOREIGN_ZOMBIE on bit 8 is deliberate. When a flag appears set with no probe from any setter, enumerate the flag table first. `trap-hand-numbered-inode-flag-bits-shared-bit-28-check-sum-equals-or`
- **`MXFS_LKF_DEMAND` was CAW-only** (before 0.75.42): dlm_caw.c CASes the sticky revoke bit, dlm/dlm.c ignored it at both NOQUEUE deny sites and denied with MXFS_ERR_DEADLOCK without BASTing the holder. On 2/tcp the pre-acquire poll expired 84/84, unlink 1.5 s to 41 s. Fix: `demand_collect_holders` + `demand_fire` BAST granted holders without queueing (probe P-DEMAND-BAST). Check a DLM flag's semantics in BOTH engines (dlm/dlm.c and dlm/dlm_caw.c) before building on it. `trap-mxfs-lkf-demand-was-caw-only-tcp-noqueue-deny-never-basts-the-holder`
- **`mxfs_v5_dlm_ag_held()` returns constant 1 on TCP**, so the stranded-AG repair was gated `is_caw` and on TCP logged `disk_held=-1 repair=0` forever; the strand lives in the local grant table and the orphan NAK refuses -EBUSY on any local entry. Peer creates timed out every 61 s for 400+ s and cascaded into four unrelated failures. Fix 0.89.74: `mxfs_v5_dlm_ag_strand_held()` (slot on CAW, `mxfs_dlm_settled_grant_nb()` on TCP). Lessons: check what a "held?" helper answers on EACH transport; a run of consecutive timeout failures usually means one stuck grant (P-LKTIMEOUT-HOLDER with growing held_ms) or a test injector (P200-STRAND-INJECT); `ag_strand_repair` arms `mxfs.ag_strand_inject=-1` on every node and an unrepaired strand poisons the rest of the run. The initial "lock-order inversion" reading was wrong. `trap-ag-held-answers-one-on-tcp-so-a-repair-gated-on-it-is-caw-only-and-a-tcp-strand-hangs-forever`

## Recurring shape (part three)

A path nobody exercises (other transport, remount, the in-barrier case, an orphan-only lock holder, a platform the harness default was never written for) hides the defect; each of these was found only after a harness or reading checked the path explicitly.
