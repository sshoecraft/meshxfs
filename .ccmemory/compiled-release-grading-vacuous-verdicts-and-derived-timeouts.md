Common thread: a verdict, budget, test or probe that looks authoritative but was never derived from a measurement, never graded a row, or never reached the state it names. Three loosely joined clusters: (A) release-run grading and derived timeouts, two lessons from 2026-10-21; (B) fence, death and survivor test design on DRBD/QNAP/tcp, harness mechanics, and the product defects those tests surfaced; (C) module load/config and probe-discriminator traps, where the configuration or discriminator a test believes it is exercising is not the one in force.

## A. Release-run grading and budgets: a number or verdict that looks fine but was never derived from / graded anything real

### A1. Own-rig configs parse only with MXFS_OWN_RIG=1; importers grade nothing  `trap-own-rig-configs-parse-only-with-mxfs-own-rig-so-importers-grade-nothing`

**The trap.** `tools/configuration.py` parses an own-rig attachment's configuration (`2/net/mesh/drbd`, the vSphere shared disk) only when `MXFS_OWN_RIG=1` is in the environment (`configuration.py:174`). `tools/criteria.py` sets it at import time **only when its own command line names such a configuration** (`criteria.py:106-113`). A Python tool that imports `criteria` and grades a DRBD configuration (no DRBD config on its argv) therefore gets `criteria.applies(entry, "2/net/mesh/drbd") == False` for every row, and any "rows that are not green" loop returns an empty list: a clean verdict that graded nothing.

**Where it bit.** `tools/release_run.py` `board_verdict` read the DRBD board as clean on every run until the 0.90.134 dry run (2026-10-21); the DRBD step still failed only because `tests/drbd_release_verify.sh` prints its own verdict line. Fixed: `board_verdict` sets the flag for an own-rig attachment (restoring it after) and refuses a verdict that graded no row.

**Same family, same day.** `tools/defects.py check_cells` looked for a `release:<step>` run in the board of the configuration it is filed under; the orchestrator writes every step's run to the primary ledger (`criteria.SPEC`), so the DRBD step's runs could never be named. Fixed to read release-step runs from the primary ledger.

**How to apply.** Any new code that imports `criteria`/`configuration` and touches an own-rig configuration must set `MXFS_OWN_RIG=1` around that call (and restore it, since child processes inherit it), and any verdict loop must count the rows it graded and refuse zero. When a grading result is "nothing bad", check it graded something before trusting it.

### A2. A test sized in seconds is an underived timeout  `feedback-a-test-sized-in-seconds-is-an-underived-timeout`

Owner correction, 2026-10-21 (session ac944f16), repeated in capitals: "ANY test that takes 3600 seconds is a fail, even if it's a buffer." "You must use actual benchmarks as baselines", not made-up numbers. Owner called the 3600 s soak "insane".

What happened: data/release_policy.json carried `soak.seconds: 3600` (written by the release-rework session as "first values"), run.sh turned it into the soak row's budget as SOAK_SECONDS+30 = 3630 s, and tests/criteria/TIMEOUT_BUDGETS.md listed the soak as "exempt, duration test, 1h+5m". The session READ that policy and reported "the one-hour soak" to the owner as a design property instead of refusing it under RULE: TIMEOUTS ARE PERFORMANCE ASSERTIONS, NOT SAFETY NETS. The dry run then graded a 31 s soak PASS against 3630 s (SOAK_SECONDS never reached the node: run_none forwards a fixed env list). (Vacuous grading again: a PASS against a budget that was never real.)

The rule as applied:
- A test's length is never a parameter in seconds. A soak, a stress, a "run for N minutes" loop is a fixed amount of work. A duration test can only fail by hanging, which is not a performance assertion.
- Its budget is measured: run the identical work on native XFS (`./run.sh 1/xfs prep_cluster`, then `./run.sh 1/xfs <row>` several times), budget = 2x the native elapsed. Record the measurement next to the budget (manifest comment, TIMEOUT_BUDGETS.md row, criteria `--why`).
- Seed any randomness in the workload so XFS and MXFS do the same work.
- Any number in a policy or config file that sets how long a test runs, or its budget, is a timeout under the rule: check it against the rule the moment you read it, and say so, never pass it along as a "length".
- "Exempt" is not a category in TIMEOUT_BUDGETS.md.

Applied: tests/suite/soak.sh is 1112 ops (median of 198 recorded runs of the old loop), RANDOM=1; native XFS 20/20/19 s; budget 40 s; MXFS 24/24/24 s on 2/net/mesh/direct.

## B. Fence, death and survivor test traps  `compiled-fence-and-death-test-harness-traps`

Common thread: a death, fence or survivor test that grades the wrong thing, never reaches the state it claims to test, or runs on a platform where the precondition does not exist. Most are DRBD-rig traps; a few are neighbours (QNAP PR keys, install path, teardown ordering, allocator floors). Newest first within each cluster where timing matters.

### B1. Death and fence tests must reach the state under test

- **Hold the lock across the death.** `drbd_rig.sh death-test` passed every session because the victim always died between CAS swaps; `crash_audit` killed it holding its bakery ticket and the survivor's swaps EIO'd after 10 s, heartbeat failed, survivor self-withdrew (`P163-WITHDRAW-STAMP`). For any lock/lease a peer can hold across its death, test death WHILE held, deterministically (`mxfs.dbg_drbd_cas_hold_ms`, `DEATH_HOLD_TICKET=1`), and check clearance by proof (`P-DRBD-CAS-PEER-EXCLUDED`). `trap-a-death-test-whose-victim-dies-between-swaps-never-tests-a-lock-held-across-death`
- **Power-off hides every release path that needs an answer.** A powered-off peer answers nothing, so the guard's release-on-answer path was dead code in `self-restart-test`. On pve1 the peer was UP with DRBD unconfigured; the guard released it 65 s in, under the survivor's own startup fence, giving `P-DRBD-STARTUP-FENCE-UNPROVEN` and a refused mount (fix 0.90.69, `own_mount_pending`). Add a variant where the excluded peer is up and answering without the service. `trap-a-survivor-test-whose-peer-is-powered-off-never-sees-the-guard-release-a-peer-that-answers`
- **Do not release a fenced peer before the survivor's witness confirms.** `drbd_rig.sh fence-test`/`split-test` released the loser's inhibit 1-2 s after the fence; the peer rebooted and reconnected before the witness saw "off AND inhibited under the receipt's episode" (`P-DRBD-EXCL-NOT-YET`, `P238-DRBD-FENCE-NOT-YET link Connected` forever). Survivor stayed fail-closed with grants frozen and its unmount blocked forever (on 0.90.106 also the put_super UAF). Fix 0.90.107: `wait_mxfs_recovered` gates every release on `P163-RECOVERY-COMPLETE` + `P238-DRBD-FENCE-WITNESSED` (~12 s). Diagnose with `journalctl -t mxfs-rig-fence` on clyde. `trap-a-drbd-test-that-releases-the-fenced-peer-before-the-survivors-witness-confirms-freezes-the-survivor`
- **A platform pass says nothing about another platform.** The QNAP purges a frozen initiator's PR key ~40 s after freeze (PRgen unchanged); death lands ~60 s, so PREEMPT AND ABORT never has a key. The only certifying fence is the witnessed LU reset, admitted only on audited kernels; on 0.89.79 a hung PVE node froze its cluster (`verdict=kernel-unaudited`) while the Ubuntu rig recovered at +78 s. Run the freeze test ON the platform (PREP=pve); test key-present fencing on a conforming target (LIO); check `scripts/pve_libiscsi_crosscheck.sh` for new PVE kernels. `trap-the-qnap-drops-a-frozen-nodes-pr-registration-40s-after-freeze-so-every-fence-there-is-key-absent`

### B2. Grading must follow evidence, not hard-coded roles

- **Symmetric fault: derive winner/loser first.** `fence_partition_reconnect.sh ARM=network` named A survivor and B partitioned; B won, and all six FAILs were attribution errors against a correct resolution. Grade roles from `fen_a`/`fen_b` (`P236-FENCE-CERTIFIED` counts), never hostnames; give the loser an instrument too. `bad_lines()` has two different bodies in two harnesses; a fence-notify shutdown is expected containment on the loser, `BUG:`/`Oops` never acceptable. A harness whose INFO says an outcome is legitimate and then counts it FAIL has two disagreeing graders. `trap-a-two-node-arm-that-names-one-node-the-survivor-grades-every-assertion-against-the-wrong-side-when-the-other-one-wins`
- **Assertions that encode the observed behaviour pass on the defect.** Live-prover mode 3 asserted the hang; the real defect was a retry gate that read only the platter. `scsipr` returned before PROUT when `arm_submit` failed (PRECOMMAND, retry armed), then `retryable()` saw `FENCE_CMD_MAY_HAVE_RUN` and disarmed, leaving FENCING + MAY_HAVE_RUN, no latch, no block, waiters hung. A durable arm can only say "may have"; whether it was issued is in-memory knowledge of the writing incarnation. Fix 0.89.63: per-slot witness `fence_boundary[slot]={victim,epoch,term}` keyed on all three fields (terms restart at 1), `retryable()` returns 2 for ours-and-armed, `P304-FENCE-RETRY-ARMLANDED`, `P238-FENCE-BOUNDARY-HELD`. Mode 3 now requires re-drive, a certificate after a completed command, and a served stat. `trap-a-retry-gate-that-reads-only-the-platter-disowns-the-arm-its-own-node-made-under-a-lost-answer`
- **A coverage floor ruled from harness shape demands what the design forbids.** The allocation-coverage witness floors (same-AG carving by both nodes, overlap, >=1 chunk release) failed at 2/tcp because `xfs_dialloc_pick_ag` pins files and dirs to the affine AG, `mxfs_ag_inode_owned` keeps nodes in their stride, and `mxfs_inode_chunk_may_delete` is false on clustered mounts. Read the allocator path and list what the design FORBIDS before ruling a floor, and put those facts in any consult prompt. Re-scoped: partition integrity, per-node >=2 carves in affine AG, span overlap, releases == 0 as invariant plus a live empty-retain-reuse lifecycle. `trap-a-coverage-floor-ruled-from-the-harness-shape-alone-can-demand-what-the-module-is-designed-to-forbid`

### B3. Harness mechanics that fake or hide results

- **Proxmox `/run` is noexec.** A slow-witness wrapper staged there failed `P-DRBDW-NOEXEC rc=-13` at once and the arm tested nothing. Stage executables in `/dev/shm` or root fs, and assert the helper actually ran; a fast verdict with empty reasons is an exec-failure signature. `trap-proxmox-mounts-run-noexec-so-a-usermode-helper-staged-there-fails-eacces`
- **Unmount the survivor before destroying the peer** when the lap's subject is the next mount. Unmount inside the 62 s dead-confirm window (31 beats x 2000 ms) hit rc=124 at a 60 s bound. Staging is identical either way. If a harness must unmount inside the window, derive the bound from window plus unmount work. `trap-unmounting-a-survivor-inside-the-peer-death-confirm-window-costs-the-whole-window`

### B4. Product-side lessons surfaced by these tests

- **Teardown: NULL-then-free protects only re-readers.** `put_super` cleared `m_mxfs_dlm`, `synchronize_rcu()`, freed the ctx while `xfs_log_worker` sat in a 20 s acquire holding it; Oops, reproduced by `tests/rig_unmount_cover_race.sh`. Cancel every worker that can be inside a call (`cancel_delayed_work_sync(&m_log->l_work)`) ABOVE the free on every path including error/skip paths (0.90.106). A directed repro must park AFTER the pointer read, or it resumes into NULL and looks like "no bug". `trap-clearing-m-mxfs-dlm-does-not-stop-a-worker-already-inside-an-acquire`
- **DRBD victim records carry no identity.** `mxfs_disklock_set_identity()` runs only under `if (ctx->pr_key)`, and DRBD registers none, so victim host/boot UUIDs are all zero (`P-BOOT-SCAN-NOIDENT`). Treat zeros as "not recorded", never compare them as "another host". The bootstrap-owner record does carry real UUIDs. A DRBD victim is bound by get_tree_bdev uniqueness, exclusive backing-device hold, and exactly two endpoints. `trap-a-drbd-victim-record-carries-no-identity-block-so-its-host-and-boot-read-as-zeros`
- **`make && make install` is the user's path.** At 0.90.42 it installed only `mxfs.ko` (no current mkfs, witness, fence-peer handler, modprobe.conf, man pages, udev); a stale 0.11.39 mkfs formatted the volume and the unfenced DRBD pair lost pve2. The node file list lives only in `mxfs_stage_node_files` (`packaging/common.sh`), shared by `install_source.sh` and `mkdeb.sh`; `mkrpm.sh` has its own copy to keep in step. Install refuses over existing .deb/.rpm/DKMS. Release claims need a clean-clone install-mkfs-mount; safety instructions must be reachable from the README and enforced by the module. `feedback-users-install-by-git-clone-and-make-install-so-that-path-must-produce-a-working-node`

## C. Module load/config and probe-discriminator traps  `compiled-insmod-module-param-and-mount-option-traps-and-wrong-discriminator-probes`

Five traps sharing one theme: the configuration or discriminator a test believes it is exercising is not the one actually in force. The first three are about loading and configuring mxfs.ko; the last two are about instrumentation and harnesses that cannot distinguish the cases they claim to.

### C1. Loading and configuring a test module

- **insmod skips modprobe.d.** Swapping a hand-built mxfs.ko onto a package node with `insmod` does not apply `/etc/modprobe.d/mxfs.conf` (`force_transport=1`, `target_cache_protected=1`). Without `target_cache_protected` the RW mount is refused (P-DOMAIN-REFUSED, rc=32), and a probe that then touches `/mnt/mxfs` runs on the underlying root-fs directory and reports a meaningless result. Load with `insmod mxfs.ko $(sed -n 's/^options mxfs //p' /etc/modprobe.d/mxfs.conf | tr '\n' ' ')`, gate every probe on `grep -q ' /mnt/mxfs mxfs ' /proc/mounts || exit 1`, restore with rmmod + modprobe. A lone mount on a LUN with an unclean slot runs whole-cluster bootstrap and waits the 62 s death timeout before replay, so a mount budget under ~150 s is killed by `timeout` and the mount aborted after it completes. `trap-insmod-skips-modprobe-d-options-so-a-test-module-mount-is-refused-and-the-probe-runs-on-the-bare-dir`
- **A charp module parameter containing a space needs literal quotes in the insmod argv.** kmod joins argv into one string and the kernel splits on whitespace in `next_arg()` (`/src/linux/lib/cmdline.c:227`), which honours `"` only if the quotes are still present. `target_retire_contract="QNAP:iSCSI Storage:..."` arrived as `QNAP:iSCSI`, and the module refused every certificate for a product mismatch it invented. Pass `'name="value with space"'` (or `ARGS+=("name=\"${VALUE}\"")` as in `tests/setup/prep_node.sh`). It was caught only because the harness read `/sys/module/mxfs/parameters/<name>` back and asserted it before grading; any harness configuring the module through a parameter should do the same readback. `trap-a-module-parameter-whose-value-contains-a-space-needs-literal-quotes-in-the-insmod-argv`
- **Documented mount options that the live parser never had.** `docs/discovery.md` and `mxfs(5)` listed ~11 options (`broadcast`, `multicast=`, `discovery_port=`, `port=`, `dlm_transport=`, `block_cache=`, `inode_cache=`, `dir_cache=`, `node_slot=`, `journal_offset=`, `disklock_offset=`) that existed only in the retired `dlm/mount.c` (`struct mxfs_mount_opts`, not in Kbuild); users got "unknown mount option". Check `xfs_fs_parameters[]` in `pal/linux/xfs_super.c` before documenting or using an option. Real knobs are module parameters (`force_transport`, `cache_mem_pct`, `inode_cache_max`, `block_cache_max`, `dead_timeout_ms`, `dirshard_mkdir_enable`; see `modinfo`) and, since 0.89.74, mount options `peers=A/B/...` (slash-separated, the option string splits on commas) and `cluster=NAME`. Discovery/lease hardcode multicast 239.66.83.1 and port defaults in `dlm/v5_mount.c`. `trap-documented-mxfs-mount-options-did-not-exist-in-the-live-parser`

### C2. Discriminators and reproductions that cannot tell the cases apart

- **A caller tag or return address names the funnel, not the caller's intent.** `xfs_buf_item_relse` exempted `why == "iodone"`, but that tag is stamped by `xfs_buf_item_done`, which nine overlay release-drain/acquire-evict arms call with no I/O. The adjacent probe printed `__builtin_return_address(0)`, always `xfs_buf_item_done` inside `xfs_buf_item_relse`; 145 firings were dismissed as benign completions because the discriminator was already discarded. Sticky provenance fields can be stale and `XBF_WRITE` is wrong the other way (`xfs_buf_ioend_fail_unsubmitted`). Fix: the caller declares the property as a parameter (`enum xfs_bli_release_ctx { XFS_BLI_NO_IODONE, XFS_BLI_IODONE_FOLLOWS }`; only `__xfs_buf_ioend` passes FOLLOWS), and change the prototype rather than adding an optional argument so the compiler enumerates call sites (it confirmed ten). Separately: closing the hole did not prove it was the leak's route (the arms are gated on dir-buffer predicates, disjoint from the AG-meta `b_ops` set; the verification lap measured zero firings). Say "unsound contract, now sound", keep the defect open. `trap-a-caller-tag-or-return-address-cannot-discriminate-callers-that-all-funnel-through-one-function`
- **A synthetic harness misses the preconditions the real criterion produces.** For D-0963 (shortform dir's deleted entry resurrected by 3-way merge), `tests/d0963_sf_dirent_resurrect.sh` ran 0/20 because (1) the platter adopt (P174-STALEGEN-ADOPT) is skipped on the node that created the directory (`sf_disk_check` requires `!i_mxfs_self_created`) and the harness had the deleter create it, and (2) the deleter's fork must stay stale-gen through its removal loop, needing the re-acquire to skip the rebuild (P34F-RELOAD-SELFAHEAD-SKIP: pin=1 ili=0x1, loaded_gen frozen while dir_gen advanced), but the harness forced the log at each handoff. The real `cache_coherency` unlink_visibility phase produced both at 1 lap in 5. Drive the real criterion in a lap loop with diagnostics armed (`tests/d0963_cc_laps.sh`) before inventing a shape; when a synthetic reads 0/N, check each probe's gate conditions against which node plays which role (self-created, pinned, post_release) instead of assuming the chain is wrong. `trap-a-synthetic-dirent-harness-misses-the-two-preconditions-the-real-criterion-produces`
